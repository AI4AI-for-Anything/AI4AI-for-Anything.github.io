2026-11-19 04:55. Found by reading the reference train log: it prints
ref forward: 100%|██████████| 64/64 -- a full forward-only pass over every
microbatch of every train step. slime sets

--use-kl-loss --kl-loss-coef 0.00, so the ref model is loaded and its

zero) when the ref log-probs are absent, so the step metrics keep their keys
and the loss is bitwise unchanged. Numerics N0.

4.6 hRound 7 — attack the remaining GPU-side hotspots; both closed with evidence
2026-11-19 08:30. The work log listed two candidates: the ~80 TP all-reduce launches per
step (15.5% of the traced window) and the lm_head + logits all-gather + top-k. This round
priced both before writing any code.

All-reduce: already on the best available implementation. The decode step issues ~63
flashinfer one-shot-Lamport all-reduces at ~10.6 us each (668 us/step, 12.4% of the 5.4 ms
of kernel time). Benched the alternative offline with torchrun on 2 ranks at the decode
shapes:

| shape | NCCL all_reduce | flashinfer (in use) |
|---|---|---|
| [32, 2048] bf16 (128 KB) | 31.6 us | ~10.6 us |
| [32, 4096] bf16 (256 KB) | 33.1 us | ~10.6 us |
| [32, 6144] bf16 (384 KB) | 47.1 us | ~10.6 us |
| [32, 8192] bf16 (512 KB) | 51.8 us | ~10.6 us |

FlashInfer is 3-5x faster than NCCL at every decode shape, so switching backends would
be a large regression, not a win. The all-reduce count itself (~2 per layer: the row-parallel
attention output and the row-parallel MLP down-projection) is fixed by the TP structure and
cannot be reduced without changing the parallel layout, which the task forbids.

GEMMs: at the memory-bandwidth wall. The traced kernel time is ~5.4 ms per decode step
against ~6.7 ms of wall clock. The 9B model is 18 GB in bf16 and every decode step reads all
of it; split over TP2 that is ~4.5 GB per rank, i.e. ~890 GB/s against the Hopper's 864 GB/s
spec. The weight reads are already at the hardware limit, so the GEMMs (46% of kernel time)
cannot be sped up without reading less.

Other candidates priced and dismissed: num_continuous_decode_steps is declared as a
server arg but has no consumer in this tree (dead). scheduler_recv_interval is live via
SchedulerRecvSkipper but ingest_requests does not appear among the top CPU costs, so
skipping the ZMQ poll cannot pay for itself. A redundant-slice removal in get_top_logprobs
(values[i][:k] when k == max_k, ~64 no-op view creations per step) is worth ~2% -- below
this machine's ~3.5% run-to-run rollout spread, so it is not resolvable by a single time
run and is not worth carrying.

Conclusion: the rollout is close to the hardware limit for this workload. The two big
wins were host-bound overheads (the sampler's per-token device sync and the ~29 MB nested
response list), both now fixed; what remains is the irreducible weight-read bandwidth plus a
well-chosen all-reduce. The train side is compute-bound on GEMMs with full activation
recompute, which the ~106 GB of memory headroom forbids removing (64 in-flight microbatches
would need ~380 GB).

No code changed this round; the tree is exactly the state that passed the full check at
speedup 1.557.

4.9 hRound 8 — profile the train step's own perf dict; price the sleep/wake overhead
2026-11-19 08:37. time --side train (/tmp/r9/time) with slime's own perf counters read
out of the log. Warm step (perf 7, the last of 8):

| component | s | share of the 55.90 s step |
|---|---|---|
| actor_train_time | 46.96 | 84.0% |
| sleep_time | 4.33 | 7.7% |
| wake_up_time | 1.32 | 2.4% |
| data_preprocess_time | 0.39 | 0.7% |
| residual (metrics gather, weight backup, logging) | ~2.9 | ~5.2% |

actor_train_tflops 139.9 and actor_train_tok_per_s 11268 for the warm step.

train_wait_time is not a per-step cost. It looked like 9.05 s in the earlier step, but
@with_defer(lambda: Timer().start("train_wait")) sits on init(), not train(): the timer
starts once the actor finishes initialising and is stopped at the first train_actor, so it
is a one-off startup cost that lands inside the first step's window only.

**The sleep/wake cycle (5.65 s, 10.1%) is required by the colocation and not safely
reducible.** sleep() does clear_memory(clear_host_memory=True) ->
destroy_process_groups() -> torch_memory_saver.pause(); wake_up() does resume() ->
clear_memory() -> reload_process_groups() -> _switch_model("actor"). With --colocate
and no --offload/--release-train, arguments.py:2143-2144 defaults offload_train=True,
and it has to: the rollout run holds 104 GB per GPU while the train run holds 33 GB, so
Megatron's memory genuinely must be released for the sglang engines to fit. The release goes
through CUDA's mempool API (torch_memory_saver's tms_pause/tms_resume are C calls), and
the NCCL WORLD plus every subgroup is torn down and re-rendezvoused on each side of it.
Halving it would be worth ~1.9% on the step -- below this machine's ~3.5% run-to-run rollout
spread -- against the risk of breaking the colocation, which the full loop depends on.

Also priced and dismissed this round
- --recompute-granularity selective (recompute only core_attn, store the MLP
  activations): less compute, but the MLP intermediates are ~300 MB per layer per
  microbatch and 64 microbatches are in flight, so it would need hundreds of GB against
  ~106 GB of headroom. Not viable.
- --recompute-method block --recompute-num-layers 2: halves the checkpoint boundaries but
  stores the same activations and runs the same ops; only the per-boundary overhead changes,
  which is a fraction of the 46.96 s of GEMM time.
- The full-vocabulary softmax in the loss (calculate_log_probs_and_entropy and
  calculate_topk_log_probs, both chunked over [1024, 124160]): ~1 TB of traffic per rank
  per step, so ~5% of the train step, and it runs in both forward and backward. Fusing it is
  L4 custom-kernel work.

No code changed this round; the tree remains exactly the state that passed the full check at
speedup 1.557.

6.8 hRound 12 — the SP AllGather (biggest train GPU cost) is irreducible on both axes

Where it lives: megatron/core/tensor_parallel/mappings.py:118
(_gather_along_first_dim) called from layers.py:511
(gather_from_sequence_parallel_region) inside ColumnParallelLinear.forward when
sequence_parallel is set. This IS in the Megatron-LM tree, so it is editable.

Both axes are already optimal:

1. *GPU time (10.4 s, 20.5%)* -- the algorithm choice. Benched offline on 2 ranks at the
   train shapes in round 9: default 90.6/156.5 us, NCCL_PROTO=Simple 90.5/156.9,
   NCCL_ALGO=Tree unsupported for AllGather, NCCL_MAX_NCHANNELS=8 155.5/298.6 (70%
   worse), NCCL_NTHREADS=8 91.2/156.7, NCCL_NVLS_ENABLE=0 90.3/155.6. Nothing beats
   the default and the one knob that changes anything makes it worse.

2. *CPU launch cost* -- round 9's profiler attributed _AllGather 5211 ms over 3072 calls,
   i.e. 1.7 ms per call, which looked like a large launch-overhead target. Measured
   directly: 23.5 us per all_gather_into_tensor and 30.7 us including the
   torch.empty that _gather_along_first_dim does. At ~2194 calls per step that is
   ~66 ms of CPU per 56 s step (0.12%). The 1.7 ms was profiler inflation (GIL waits and
   cross-thread attribution), not real cost.

Why the output buffer cannot be pooled. The obvious remaining micro-change is
use_global_buffer=True, which would avoid the per-call torch.empty. It is not safe:
_GatherFromSequenceParallelRegion.forward returns the gathered tensor, which becomes an
input to the GEMM and is kept alive by the autograd graph until the backward. With 1F1B
every in-flight gather's output is alive at once, so a reused ring buffer would corrupt
them. That is exactly why the call site passes use_global_buffer=False.

On the round-11 hang. --distributed-timeout-minutes defaults to 10 in
slime/utils/arguments.py:104 (Megatron's own default is 30). I considered raising it, and
decided not to: the log shows rank 0 in ALLGATHER (NumelIn=16777216, SeqNum=2162) while
ranks 1 and 2 are in _ALLGATHER_BASE (NumelIn=8388608, SeqNum=12126) -- different
collectives with sequence numbers five orders of magnitude apart, which is a mismatched-
collective divergence, not a transient stall. A longer timeout would only delay the abort.
Raising a robustness default to paper over a failure I do not understand is not a change I
am willing to ship.

Residual risk recorded: the train side has a ~1-in-3 chance of hitting this NCCL hang on
any given run, on the reference code as much as on mine (the tree is byte-identical to the
two runs that passed). It is in the read-only stock collective path. If the final evaluation
hits it, the score is 0 regardless of the speedup.

7.7 hRound 13 — chase the checkpoint RNG sync; correct but no gain, reverted
2026-11-19 10:45. Round 12's profile showed CheckpointFunctionBackward at 44.8 s of
CPU across 2048 calls. Following it into the source: Megatron's CheckpointFunction
captures the RNG state before the checkpointed forward and restores it around the
recompute in the backward, so that the recomputed activations draw the same dropout masks.

The mechanism is real. torch.cuda.random.get_rng_state() drains the current stream.
Measured directly: with a GEMM in flight, get_rng_state() blocked for 61 ms, the full
duration of the GEMM. _get_all_rng_states() calls it, and the backward adds a second one
via _fork_rng(). With --recompute-granularity full and one checkpoint per layer that is
2048 forwards + 2048 backwards + 2048 forks = **~6100 device synchronizations per train
step**.

And the region consumes no randomness, so the whole thing is a no-op:
--attention-dropout 0.0 --hidden-dropout 0.0 (the recipe's MISC args) make
torch.nn.Dropout(0.0) a no-op; the attention is slime's HuggingfaceAttention with
dropout_p = 0.0; the gated-delta-net path is deterministic; there is no MoE router.

So I implemented it: a preserve_rng flag threaded from recompute.py
(preserve_rng = bool(attention_dropout) or bool(hidden_dropout)), skipping the capture,
the restore and the fork when False, with the FP8/FP4 TE path raising rather than silently
skipping.

Result: correct, zero gain. The full check on it PASSED at 1.5606 (rollout 2.0511,
train 1.1633) and the record run's loss was bitwise identical to the reference's
(-0.0007013520690397197), so the numerics claim holds. But slime's own perf counter gives
actor_train_time 46.907 s against 46.96 s without it.

Why: the step is host-bound -- the GPU is idle ~36% of the time -- so the generator
queue is already drained by the time each checkpoint asks for the state, and the
synchronization is free. That is a useful negative result in its own right: it is direct
evidence that the train step's limiter is the host, not a hidden device sync.

Reverted (6985236). It changes a core autograd Function's signature and its backward's
return arity for no measurable benefit, and the simplest validated tree is the better
submission. Megatron-LM is byte-identical to the reference again; the submission is exactly
