6.4 hRound 11 — expensive lever attempted: fused-RoPE rewrite (measured regression, reverted)
- The hook correctly pushed me to actually attempt a rewrite. Candidate: apply_rotary_pos_emb builds rotate_half(q)=cat(-x2,x1) (a full copy) then multiplies; I rewrote it to compute the two half-dim outputs directly (q1·c1 − q2·s1, q2·c2 + q1·s2).
- Bitwise: verified identical — standalone test across dtypes (bf16/fp32/fp16) and shapes: (-a)*b == -(a*b) and a+(-b) == a-b in IEEE fp32 (neg is exact), so it reproduces (q*cos)+(rotate_half(q)*sin) exactly.
- But measured (microbenchmark at the real query shapes) it is a net regression: text-gen query [4,H,128] = 102.9 vs 72.0 us/call (1.42× slower); image-gen query [1024,H,128] = 153.6 vs 162.1 us/call (0.95×, slightly faster). The step is CPU/launch-bound and the text gen calls RoPE ~580×28× more often than the image gen, so the 7-launch rewrite (vs the original 5) loses far more than it gains. Reverted.
- Lesson recorded: on a launch-bound step, "fewer intermediate tensors" rewrites that add kernel launches regress; the original RoPE was already lean. Submission unchanged (cca2df7, full-check PASS 1.1185 N0).
6.5 hRound 12 — expensive lever attempted: L4 Triton fused-RoPE kernel (fast but N1, reverted)
- The hook correctly pushed me to actually attempt a custom kernel. I wrote a Triton kernel fusing the whole RoPE (both q and k) into one launch (vs the original ~10 ops/kernels), computing the two half-dim outputs with the rotate_half partner.
- Fast: 2.6× (text-gen query [4,H,128]), 6.2× (image-gen query [1024,H,128]) — a real launch reduction on the launch-bound step.
- But not bitwise (N1): a persistent ~1-ULP fp32 mismatch vs PyTorch's separate-kernel (q*cos)+(rotate_half(q)*sin). Preventing LLVM's FMA contraction with inline-asm mul.f32/add.f32 (the documented way to match library rounding) reduced but did not eliminate it. That 1-ULP fp32 delta flips the downstream bf16 cast on rounding-boundary elements and would propagate into gate 2 (not N0).
- Conclusion (now demonstrated, not asserted): a fused elementwise kernel cannot cheaply reproduce PyTorch's per-op rounding bit-for-bit here, so the L4 lever is blocked by the N0 constraint. Submission unchanged (cca2df7, full-check PASS 1.1185 N0).
- bf16-absorption check: the RoPE output is cast to bf16 downstream, so I tested whether the 1-ULP fp32 delta is absorbed. It is not — 3772 / 401M elements (0.0009%) still differ after the bf16 cast, which would propagate into the parameters and break gate 2. Confirms the kernel is unusable under N0.
