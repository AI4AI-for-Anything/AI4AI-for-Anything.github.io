Change (commit 9db8792, yoco/models/fast/rmsnorm.py, switch YOCO_FAST_RMSNORM=1): one Triton kernel for
the forward, one for the backward, the weight gradient with two ATen ops. To be bitwise for the same inputs the
kernels reproduce ATen's arithmetic step by step: the row reduction order of torch (one warp per row; for D > 128
four accumulators per thread, the lanes of the 4-element vectors, joined from the left, then the warp tree in the
order 1, 2, 4, 8, 16; for D = 128 thread accumulators lane + 32 i), mean = sum × float(1/D), rsqrt as
tl.math.rsqrt (same instruction as torch), no FMA, the backward's r ** 3 on the saved output, × -0.5, the
division by D as a multiplication by float(1/D) (what ATen's div.Scalar does), and every bf16 rounding of the
reference in place. Probes: bitwise for D = 3072/256/384/512 and 128, affine and not, on forward, input gradient
and weight gradient; the first real call of every configuration is compared with the reference forward.

Kernel versions (forward / backward GPU time, profiler): affine D = 3072 13.8 / 20.6 µs (ATen: 118 / 166),
D = 128 76 / 74 µs (ATen: 102 / 95; bound by about 261 shuffles per program, not by memory). Rejected: lane-leading

Check: check --quick (/tmp/r7/quick/check.json, 14:26): gates 0 and 2 pass, every exact item passes, but
not bitwise: 1277 of 9616 recorded tensors identical, 666 beyond the per-tensor thresholds (first at update 0:
gradients of the cross-decoder layers' q_proj weights, 0.76 %), measured tier N1. Debug runs in a copy of
the tree (every forward and backward of the first 700 norm calls compared with the reference on the same inputs:
/tmp/r7/dbg in production, /tmp/r7/quickdbg in deterministic mode) printed no mismatch, and the first
commit message therefore claimed N0 wrongly.

Cause (found 15:05 with /tmp/dev/probe/accum_test6.py): the norm's input is also read by the residual add.
Autograd's engine sums the reference norm's *two* bf16 gradient contributions (the x.float() * r branch and the
rsqrt branch) into the gradient buffer of the input's producer, in arrival order, after the residual's gradient:
(G + gs) + gxf. The fused backward hands over one tensor, so the buffer holds G + bf16(gs + gxf): the same
sum with one rounding moved, different in about 15 % of the elements by one bf16 ulp. With a leaf input (two
contributions) the order does not matter, which is why every per-call comparison was bitwise. A bitwise variant
would need a second autograd node per norm (e.g. a view of the input passed as a second argument) and with it
the engine's extra bf16 add per norm back again (55 per update, about 0.7 ms of GPU time and 1 ms of host time).
Not done: tier N0 brings no safety here (the bitwise candidates already deviate 0.3–0.8 σ in gate 3 from
production nondeterminism: /tmp/r5/full, /tmp/r6/full) and would cost about 1 % of the speed.
The change is a reorder of bf16 additions: tier N1, decided by gate 3.

JITFunction.run of Triton 2.3.1 is replaced. The first launch of a call shape goes through Triton's function

parameters, a grid that is not a tuple or a function of the arguments, tensor maps) keep Triton's function.
