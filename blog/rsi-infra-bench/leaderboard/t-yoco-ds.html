### Changes (all bitwise-neutral by construction, i.e. intended N0)

1. YOCO_NO_OSS=1 - fairseq.optim.shard_ becomes a no-op, so the fp32 Adam state is replicated instead of
   sharded. Every rank runs Adam on the whole parameter set: per-parameter arithmetic, kernel and shapes are the
   same as on the owning rank before (gradients are bitwise identical on both ranks after the 2-rank all-reduce),
   so the updated fp32 masters and bf16 weights are bitwise identical; the 13.6 GB one-directional fp32 shard
   broadcast (38.5 ms) disappears. Cost: Adam does 2x the parameters (14.4 -> 28.8 ms) and +27.2 GB state memory
   (peak 61.75 -> 74.5 GiB).
2. YOCO_SKIP_ZERO=1 - FP16Optimizer.zero_grad no longer zero-fills the 13.6 GB fp32 master gradient: it is
   fully rewritten (copy_ / zeros) by _sync_fp16_grads_to_fp32() before any read. Saves the ~4.6 ms fill.
3. YOCO_FOREACH_MUL=1 - FairseqOptimizer.multiply_grads uses torch._foreach_mul_ over the fp32 grads
   (same elementwise multiply, one multi-tensor kernel instead of ~240 launches).

0.7 hRound 2 - 06:20-06:45
### Change

YOCO_FUSED_CLIP=1: fuse the fp32 master-gradient cast with the gradient scaling.
Reference order in FP16Optimizer.clip_grad_norm: (1) cast every bf16 grad to fp32 (one copy kernel per
tensor, 20.4 GB), (2) apex multi-tensor L2 norm over the fp32 grads (13.6 GB read), (3) _unscale_grads multiplies
every fp32 grad by _multiply_factor (27.2 GB read+write). Since bf16->fp32 is exact, the total norm is bitwise
identical when computed directly over the bf16 grads (same apex kernel, same per-tensor shapes, verified bitwise
in a live run), and torch.mul(bf16_grad, factor_f32.view(1), out=fp32_grad) is the exact cast plus the fp32
multiply in one kernel.

Gotcha found by gate 2: the first version was N1, not N0 (1749/9616 bitwise). Root cause: total_norm from
apex's L2 norm is float64, so _multiply_factor is a 0-dim float64 tensor. The reference's per-tensor
p.grad.mul_(f64_0dim) computes in float32 (the 0-dim scalar is rounded to float32), while
torch.mul(bf16, f64 1-D, out=f32) makes TensorIterator compute in float64 -> 1-ulp differences in ~0.16% of
the elements, amplified over the 60 fast-forward updates. Fix: pass the factor as a 1-element 1-D float32
tensor (.float().view(1)). Verified in isolation: f32*f64-0dim, f32*f32, and fused bf16*f32-1D out=f32 are
bitwise identical; the double path differs.

### Result

- time /tmp/r2/time2 (pre-fix): speedup 1.1502, 0.2035 s/update (round 1: 1.1152 / 0.2099). Saved ~6.4 ms for
  the fused pass + bf16 norm.
- check --quick /tmp/r2/quick (pre-fix): status PASS but measured_tier N1, 1749/9616 bitwise -> gate 3 would
  have decided. With the factor-dtype fix the same path is expected N0 (verified in round 3).
- git commit 4eaf2e9 (pre-fix, N1). The dtype fix is committed in the next round.
