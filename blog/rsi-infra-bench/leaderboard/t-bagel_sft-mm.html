2.0 hRound 7 — packed attention with FlashAttention, one call per split (N1, off by default)
Start: 2026-11-10 04:56Z.

Idea: upstream computes the packed attention with one dense-mask
scaled_dot_product_attention per sample, which runs the Ampere cutlass
memory-efficient kernel (fmha_cutlassF_bf16_aligned_64x128_rf_sm80) at ~30-50 TFLOP/s.
Attention is 560 ms of the 1861 ms of compute per step.  The mask, however, has a very
specific structure: inside a sample, a query of a split sees the *non-noise* splits that
come before it and, inside its own split, the lower triangle for a causal split and
everything else.  That is exactly a decomposition into per-split FlashAttention calls
(flash_attn_func, causal aligned to the bottom-right corner for the causal splits),
which also skips the masked-out blocks.

The batch may not change (the judge hashes every field of SimpleCustomBatch), and the
dense mask is the only per-sample attention information that reaches the model, so the
split structure is recovered from the mask itself (modeling/bagel/attn_split.py):
the growth of the number of visible columns per row and the columns that disappear give
the split boundaries and their modes.  Two adjacent causal splits are merged (they
produce the very same mask).  The recovered structure is checked against the mask
(BAGEL_FLASH_ATTN_VERIFY, default on) and the dense-mask path is used when it does not
reproduce the mask exactly.

Offline validation: 3000 random split structures (and 1000 with unit-length splits) —
the recovered structure rebuilds the mask bitwise in every case.

Numerical check on the GPU (one sample, 2330 tokens, 28 heads, head_dim 128):
* relative L2 difference against the dense-mask SDPA path: 8e-4 .. 2.9e-3 (bf16 level,
  the same order as the compiled RMSNorm change that passed gate 2b).
* speed of the attention itself: dense-mask SDPA 0.758 ms -> FlashAttention 0.212 ms
  (3.6x).

Switch: BAGEL_FLASH_ATTN=1 (default off) in /submission/switches.json.

5.5 hRound 22c — `NO_AC=7` (the memory wall)
/tmp/r24_time (killed): with 7 more layers un-checkpointed the peak reaches 135-142 GiB of the
143.7 GiB card, the allocator starts to thrash (0.47 steps/s at step 20 vs 0.68 at step 7) and the

from run to run (and that caused the 5.2 s stall of round 17's NO_AC=14 run).

### Ruled out in this round (measured, not guessed)

* The H2D copy of the batch is not a lever.  A CPU-only run of the judge's data pipeline
  (/tmp/mask_size.py) shows that a batch is ~150 MB, of which **134 MB is the dense attention
  masks** (3-5 tensors of [sample_len, sample_len] float32; the samples are 2.3k-3.9k tokens).
  Micro-benchmark (/tmp/h2d_bench.py): 134 MB pageable H2D = 7.2 ms, pinned = 2.6 ms, and pinning

  <1%.

  PYTORCH_CUDA_ALLOC_CONF_EXPANDABLE_SEGMENTS not being a compile-time flag in the wheel), so
  round 17's NO_AC=14 instability (6.7% window range) vs round 22b's stable run (0.62%) was
  run-to-run variance, not the allocator option.  NO_AC=14 stays rejected: the final
  evaluation uses another data seed and a 6.7% window range is INVALID (score 0).

7.9 hRound 35 — the VAE side stream: root cause hunt, and the decision to drop it
Start: 2026-11-10 10:31Z. End: 11:05Z.

The VAE-on-side-stream tree diverges to NaN on the interleaved data (gate 2b).  Three experiments,
all with the judge's own gate-2b runner (/tmp/run_conform.py, 8-16 steps):

* VAE off, EMA on (/tmp/cf_vaeoff): no NaN; the manual statistic against the frozen
  reference is r_n=0.0089, r_j=0.0069, r_b=0.0056, bound 0.0169, ratios 1.58/1.22 -> conforming.
  The EMA overlap is fine.
* VAE on, EMA off (/tmp/cf_emaoff): NaN again -> the VAE stream is the culprit.
* VAE on + a new diagnostic (BAGEL_VAE_DEBUG3, /tmp/cf_vaedbg3): the diagnostic captures the
  VAE's internal mean (through a torch.randn_like spy) during the side-stream encode and
  re-computes the encoder on the compute stream afterwards.  Result:
  mean_diff=0.0 (the VAE's internals are bitwise identical), the input images' checksum is
  unchanged, the reconstructed latent matches the stored one to 1.4e-6 (bf16 rounding only),
  and the run did not diverge.  The added diagnostic work changes the timing, so the
  divergence is timing sensitive.

Everything that could be checked was checked and came out clean: the stream ordering
(wait_stream/wait_event/record_stream), the H2D copy (the images are pinned, but
Tensor.to(device) with non_blocking=False is synchronous), the RNG (the judge keys the noise
by the call's ordinal, so the stream cannot change it), the VAE's weights (frozen, never freed)
and the autocast cache (the frozen weights are not cached).

**Conclusion: an unexplained, timing-sensitive race between the VAE's side stream and the
compute stream.**  Two full checks have rejected it.  The overlap is worth 2.4% of the speedup,
which is not worth an unexplained race, so the VAE side stream is switched off.  The code stays
in the tree behind BAGEL_VAE_OVERLAP (default off) for the record.

8.3 hRound 38 — batched varlen FlashAttention for the packed attention
Start: 2026-11-10 11:20Z.

The profile says the step is CPU-bound (every rank's python thread is ~100 % busy, 113 ms of
GPU idle in 14 701 small gaps per step, 11.5 k allocations/step -> 55 409 cudaEventQuery
calls/step in the allocator).  The packed attention issues **one FlashAttention call per split
per layer** (840 forward + 1008 backward calls per step) plus the torch.cat of the visible
keys of every split.

Idea: the splits of a sample are contiguous and a split sees the *non-noise* splits before it
plus itself, so the visible keys of a split are the prefix of its sample **unless a noise split
precedes it.  All the prefix splits of a layer can therefore be computed by a single
flash_attn_varlen_func call per mask kind** (causal / not): the queries of the splits are
gathered into one buffer, their visible keys into another, and the split boundaries become the
cumulative sequence lengths.  The splits that follow a noise split keep the per-split path
(their visible keys have a hole).

The plan depends only on the split structure, which is the same for every layer of the step, so
it is built once per step and cached.

Implementation: modeling/bagel/qwen2_navit.py, behind BAGEL_VARLEN_ATTN (default off).

8.3 hRound 38 — the batched varlen FlashAttention: **1.4769x**
Start: 2026-11-10 11:20Z. End: 12:25Z.

Why.  The profile of the step (r30 trace, /tmp/r30_profile/timing_profile.trace.json, one
step of 1823 ms) says the step is GPU-work-bound, not launch-bound: the union of the busy
intervals of all the streams is 1710 ms of the 1823 ms step (the GPU is 94 % busy) and the idle
is 113 ms spread over 14 700 gaps of ~7 us.  The compute stream (1403 ms) is:

| op | ms/step | calls/step |
|---|---|---|
| aten::mm (the GEMMs) | 746.8 | 2608 |
| FlashAttention backward | 105.5 | 1008 |
| aten::_index_put_impl_ | 73.1 | 1964 |
| FlashAttention forward | 65.0 | 690 |
| aten::index | 63.1 | 716 |
| aten::fill_ | 38.3 | 1661 |
| aten::add_ | 38.1 | 1590 |

and the GEMMs run at 652 TFLOPS while a plain linear of the same shape reaches 730 TFLOPS on
this GPU, i.e. the GEMMs have no headroom — the attention and the packing do.

The attention was the biggest reducible item.  Upstream's packed attention needs **one
FlashAttention call per split of every sample** (690 forward + 1008 backward kernels per step),
and every one of them slices the packed query/key/value, so the **backward of every slice
allocates a zero buffer the size of the whole packed tensor** (aten::slice_backward ->
aten::zeros): 1232 of the 1661 fill_ calls and 1232 of the 2664 copy_ calls of the step
come from there, and they cost ~50 GB of memset per step.

The change.  The visible keys of a split are the *non-noise* splits before it plus the split
itself, so for every split that is not preceded by a noise split they are exactly the prefix
of its sample.  All the prefix splits of a layer can therefore be computed by **one
flash_attn_varlen_func call per mask kind** (causal / not): the queries of the splits are
gathered into one buffer, their visible keys into another, and the split boundaries become the
cumulative sequence lengths.  The splits that follow a noise split keep the per-split path.

Two details that had to be right:

* FlashAttention's varlen causal mask is aligned per sequence to the bottom right (verified
  against flash_attn_func with seqlen_q != seqlen_k: bitwise identical), which is exactly
  the mask of a causal split.
* index_select's backward adds the rows with atomics, so the rows that several splits share
  are summed in an arbitrary order — not reproducible even with
  torch.use_deterministic_algorithms(True).  The gather therefore uses a custom autograd
  function whose backward accumulates with index_put_(accumulate=True) (sorted, reproducible),
  and the scatter uses one whose backward is a plain gather.

modeling/bagel/qwen2_navit.py, behind BAGEL_VARLEN_ATTN (default off).

Validation (unit test, 3 layouts, out/dq/dk/dv against the per-split path):
all prefix and single split are bitwise identical, noise in the middle differs by
4e-3 relative in dk/dv only (the bf16 accumulation of the shared key rows).

* time --config /tmp/sw_varlen.json (/tmp/r38/time): **1.7608 s/step,
  speedup_vs_frozen_reference 1.4769**, beyond_reference_noise: true, window range 0.5 %,
  peak allocated 86.2 GiB, reserved 134.3 GiB.  (The EMA-only tree: 1.8128 s/step, 1.4346x.)
* the judge's own conformance runner on the interleaved data (/tmp/cf_varlen):
  conforming — r_n=0.00768, r_j=0.00654, r_b=0.00612, bound 0.01837, ratios 1.25/1.07.

9.8 hRound 40 — the varlen attention also covers the splits whose visible keys have a hole
Start: 2026-11-10 12:20Z.  End: 2026-11-10 12:50Z.

Profile findings (r30 trace, 1 step = 1823 ms, GPU busy 94 %): the step is GPU-work bound.
Per step: GEMMs ~674 ms (at 652 TFLOPS, i.e. no headroom), all-gathers ~307 ms and

Change: _build_varlen_plan now makes *every* split one sequence of a varlen call, not

noise split sees its visible keys with a hole (the noise span is skipped); the plan gathers

of the ranges of a split), not the per-range lengths.
