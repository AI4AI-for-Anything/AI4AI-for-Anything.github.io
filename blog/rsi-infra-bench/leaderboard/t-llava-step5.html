### Dead ends measured this session
- LLAVA_TOKEN_LENGTHS (word count → token count as the sampler's length key). Simulated the real
  get_modality_length_grouped_indices + split_to_even_chunks on the timing fixture: word key 32.9%
  mean padding, token key 32.9%, true-length key 33.1% — no difference. The megabatches come from
  torch.randperm, so the key only re-orders inside a megabatch; the step's sample multiset is
  unchanged (verified), but the padding is not improved. Reverted.
- Re-partitioning the 32 samples of a step between the two GPUs. The step time is
  16 x max(L) for whichever GPU holds the longest sample, and that sample is in the step whatever the
  split, so no partition beats 16 x L_max. The only real fix is to stop padding at all (run the LLM
  on the packed token layout), which is a rewrite of LlamaModel/LlamaDecoderLayer/attention/loss.
—Round 5 — packed (unpadded) sequence layout (`LLAVA_PACKED`)
The reference pads every micro-batch to its longest sample: the trace shows
index_first_axis gathering a [13600, 4096] slice out of [17808, 4096], i.e. **23.6% of every
padded token is padding**, and all of it goes through the projection GEMMs, the layernorms, the MLP and
the residual.  Re-partitioning the 32 samples of a step between the two GPUs cannot fix it (the step
time is 16 x L_max whichever GPU holds the longest sample), and changing the sampler's length key
does not either (measured).  So the layout itself changes:

* prepare_inputs_labels_for_multimodal concatenates the per-sample embeddings / labels / positions
  instead of padding and stacking them, and returns a [1, total, hidden] tensor (the samples, their
  order and their contents are untouched — gate 0 still sees the reference's own partition).
* LlamaFlashAttention2._flash_attention_forward is patched to call flash_attn_varlen_func with the
  batch's cu_seqlens — the same call the reference makes after unpad-ing, so the attention is
  unchanged and the whole unpad/pad round trip disappears.
* the loss is the same mean cross entropy over the same supervised tokens, shifted per sample instead
  of across the padding.

Correctness checked on a real LlamaDecoderLayer: equal-length batches are bitwise identical to
the padded reference, unequal lengths differ by 2 bf16 ULP (only the cuBLAS tile selection for a
different M).  Two bugs found and fixed on the way: cumsum promotes to int64 (flash-attn rejects a
non-int32 cu_seqlens), and ModelOutput.loss = x does not add the loss key when it was None.

—Round 20 — DeepSpeed's optimiser prologue, with the class name actually right
Root cause of two earlier null results: the ZeRO-1/2 optimiser class in
deepspeed.runtime.zero.stage_1_and_2 is DeepSpeedZeroOptimizer, not
DeepSpeedZeroOptimizer_Stage2.  Rounds 16 and 19 both imported the latter, the try/except in
install() swallowed the ImportError, and both "patches" were never installed — so their null
measurements said nothing about the ideas.

With the name fixed, and a print added to prove the patch fires (`loss_scale=1.0 clip_grad=0.0
norm=6.697 -> scale=1.0`, 75 calls per run):

1. unscale_and_clip_grads skipped when combined_scale == 1.  bf16 → loss_scale is exactly 1.0
   (DeepSpeed asserts this for any dtype but fp16) and clip_grad is 0.0 (the recipe has no gradient
   clipping), so the loop multiplies the 3.4-billion-element flat gradient partition by exactly 1.0 —
   15 ms of pure bandwidth.  time: 1222.1 → 1216.0 ms.
2. get_grad_norm_direct fused: it converted every parameter's gradient to double, took the L2
   norm and called .item() — an fp64 copy and a device→host sync per parameter, ~160 of each per step,
   plus 295 fp64 reduction kernels.  One torch._foreach_norm per 128 tensors with a single host read
   replaces it.  The norm is unused (clip_grad == 0), and the patch falls back to the original whenever
   clip_grad is non-zero and the norm comes within a tenth of it, so the clipping decision is preserved.
   time: 1216.0 → 1193.8 ms.

—Round 23 — one-pass RMSNorm forward (`LLAVA_FUSED_NORM`, extended)
The norm's forward was _var_kernel + torch.rsqrt + _scale_kernel: the variance kernel read the
input, then the scale kernel read it again.  Folding the variance, the rsqrt and the weight
multiply into one kernel moves 2x the tensor instead of 3x.  tl.math.rsqrt is bitwise torch.rsqrt
on fp32 (verified), so the forward is bitwise identical to the two-kernel version — verified for 6
shapes.  Isolated 119.8 → 76.0 µs per norm (44 µs × 65 norm calls/step ≈ 2.9 ms).
time: 1181.4 → 1182.7 ms/step — no measurable gain (below the 0.35% run-to-run spread); kept
because it is bitwise-safe and strictly less work.
—Round 24 — fused AdamW master-weight tail (`LLAVA_DS_ADAM`) ← the round's win
_multi_tensor_adamw ends the step with four full passes over the fp32 master partition —
_foreach_sqrt (out-of-place, allocating a fresh 6.8 GB buffer), _foreach_div_, _foreach_add_,
_foreach_addcdiv_ — 10x the partition in bytes, where one pass suffices (denom is consumed by
nothing but the addcdiv).  DeepSpeed's ZeRO-2 hands the optimizer **one flat fp32 partition per param
group**, so one Triton kernel replaces all four: 21.96 → 6.06 ms per 6.76 GB partition, ×2 partitions
per rank.  time: 1182.7 → 1154.1 ms/step, speedup 2.4014 (was 2.3435); peak memory unchanged at
119.36 GiB (the transient denom buffer is gone, which frees ~13.5 GB of transient fp32).

Numerics — N0 (bitwise).  Three separate rounding traps had to be closed, each found by isolating
the op:
1. tl.sqrt is sqrt.approx.f32 (~2 ULP) → a 6.7e-5/step systematic loss drift.  tl.math.sqrt_rn
   is libdevice's IEEE round-to-nearest and is bitwise torch.sqrt.
2. PyTorch's tensor / scalar is a multiply by the fp32 reciprocal, not a division;
   div_rn is its tensor/tensor division.
3. LLVM contracts a*b + c into an FMA; PyTorch's addcdiv does not.  mul_rn/add_rn pin it.
Result: 3 of 131072 master weights differ over 20 AdamW steps, by 3.6e-12, and a whole 25-step run's
logged losses are indistinguishable from the unpatched tree's — two *identical* runs differ by more

A crash found and fixed (important): patching at import time made the run die with
ERROR: Unexpected segmentation fault encountered in worker, 3/3 times.  Cause: DeepSpeed's ZeRO-2
constructor (initialize_optimizer_states) runs one AdamW.step() to create the optimizer state,

workers are forked after that, and a forked child of a process that has loaded a Triton module into its

training loop (after the fork) and never hits it.  Fix: arm the patch on the first
DeepSpeedZeroOptimizer.step (the wrapper unhooks itself), so it is applied after the fork and before
anything is timed.  That pre-fork step leaves the master weights untouched (its gradient is zero), so
the numerics are unaffected.  check --quick PASSES.
