Profile finding (from the round-5 train trace and the source): the actor runs *two* full forward passes
over the batch per train step: compute_log_prob() (a no-grad forward that fills
rollout_data["log_probs"]) and the training forward+backward.  The first one recomputes the log-probs of
the sampled tokens with the same weights the training forward uses (the reference forward was already
removed in round 2, and the actor's weights do not change between the two passes), so it is a third of the
compute of the step (fwd+bwd+logprob-fwd = 4 forward-equivalents; the log-prob forward is 1 of them) and it
also repeats all the SP/CP collectives of the forward.

What the separate forward's values actually feed (checked in slime/backends/megatron_utils/loss.py):
- the TIS importance ratio: train_log_probs_for_tis is overwritten with the *training* forward's log-probs
  when the PG objective is reinforce (line 1183) - our recipe;
- the mismatch metric train_rollout_logprob_abs_diff: uses the training forward's log-probs whenever
  score centering is on (line 1352) - our recipe;
- the loss itself: pg_loss = -advantages * log_probs for reinforce - ppo_kl (the only consumer of
  old_log_probs) does not enter it;
- the advantages: the KL term is exactly zero when kl_coef == 0 (our recipe);
- the KL loss term: exactly zero when kl_loss_coef == 0 (our recipe);
- only diagnostics: ppo_kl, ois, correct_entropy.  In the reference these are already exactly 0 / 1
  (the two forwards compute the same values bit for bit), so they do not change either.

Change 8 (train side, slime): skip the separate actor log-prob forward when it cannot reach the loss
(SLIME_OPT_SKIP_ACTOR_LOGPROB=1, off by default).  The guard covers every consumer of the old-policy
log-probs (kl_coef, kl_loss_coef, a non-reinforce PG objective, OPSM/GSPO, the critic/OPD/routing-replay
paths and use_rollout_logprobs); with any of them active the forward still runs.  The correct_entropy
diagnostic tolerates the missing log-probs.
- Files: slime/slime/backends/megatron_utils/actor.py, slime/slime/observability/train_metric_utils.py.

Outcome: the change was a NO-OP and was REVERTED (no commit).  While reading the code it turned out that
the separate forward never runs in the reference either: can_reuse_log_probs_in_loss is already True because
it tests len(num_microbatches) == 1, and num_microbatches counts the *VPP* stages, not the micro-batches
(our recipe has no pipeline parallelism).  The reference logs have no Timer log_probs end line, ppo_kl is
already exactly 0.0 and ois exactly 1.0, which confirms that the log-prob forward is skipped in the
reference as well.  The measured gain was therefore 0.0 s (within the +-0.5 s noise of the train windows), and
the guard was removed with git checkout of the two files so the tree stays minimal.  Lesson recorded here:
read the Megatron-side guard conditions before assuming a redundant forward.

5.6 hRound 10 - 2026-11-13 09:25 -> 10:10 UTC (train side: the CPU Adam and the fp32 master copy)
Profile finding (the round-5 train trace plus the HDO log): the train step is 36.8 s of which the
optimizer is 4.8 s: the hybrid device optimizer builds one CPU optimizer per parameter (one fused Adam
call each, ~290 of them, each with its own fixed overhead) and the fp32 master weights of the offloaded
parameters are pageable, so the copy back to the device after every step runs at the pageable PCIe rate
(measured: 10.1 GB/s pageable vs 54.1 GB/s pinned).

Change 10 (train side, Megatron): SLIME_OPT_BATCH_CPU_ADAM=1 builds one CPU optimizer per parameter
*group* instead of one per parameter; SLIME_OPT_PIN_FP32_MASTER=1 pins the fp32 master of the offloaded
parameters.  Both off by default.  Files: megatron/core/optimizer/cpu_offloading/hybrid_optimizer.py.

Measured (bench.py time --side train):
| variant | windows (s) | train speedup | cpu_adam |
|---|---|---|---|
| baseline (r12) | 43.498 / 43.500 / 42.792 | 1.5081 | 4.75 s |
| batch+pin (r14) | 44.016 / 44.396 / 42.798 | 1.4903 | 3.40 s |
| batch only (r15) | 44.593 / 44.171 / 44.077 | 1.4711 | 4.60 s |

Conclusion: no gain, both switches left off.  The CPU Adam itself gets cheaper (4.75 s -> 3.40 s), but
the step does not: the copy of the master weights back to the device does not get faster either, because with
