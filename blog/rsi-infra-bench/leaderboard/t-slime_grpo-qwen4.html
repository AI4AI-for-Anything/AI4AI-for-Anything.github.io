1.9 hRound 4 — one pinned D2H per top-k field, at the real site (rollout side)
Start 08:24, GPU lock 08:30. End 08:44.
0.6 hHotspot (kind 1: per-row host copies; Round 2's hypothesis moved one layer down)
GenerationBatchResult.copy_to_cpu (sglang/python/sglang/srt/managers/utils.py) runs
_async_d2h on every request's top-k row: at bs≈31 and k=128 that is 62 pinned-host
allocations + 62 512-byte cudaMemcpyAsync launches + 62 record_stream calls per decode step.
async_d2h (srt/utils/common.py:562) allocates a *fresh* pinned tensor each call, and PyTorch's
caching host allocator polls every outstanding copy event on each allocation — so the cost is
super-linear in the number of rows.
Direct evidence that this is host-bound: during a rollout each sglang::scheduler process sits at
~98% of one core (96 cores available, load ~8), while the rollout profile shows only ~4.9 ms of GPU
work per ~9.4 ms decode step.

### Change

_async_d2h_topk_rows(rows): get_top_logprobs_raw leaves each row as values[i][:k], i.e. a view
of one [bs, k] topk tensor. When every row is a contiguous 1-D CUDA view of the same storage at
consecutive offsets, one as_strided((n, k), (k, 1), offset) covers them all → one pinned
allocation and one D2H, then per-row views of the pinned buffer. record_stream still records the
same original storage, so lifetime safety is unchanged. Anything else (mixed k, non-tensors,
independent tensors, CPU tensors) falls back to the exact original per-row path.
Opt-in SGLANG_OPT_BATCH_TOPK_COPY=1. Commit 7a74b4b (sglang).
Correctness checked on GPU against the per-row path for: uniform-k views, idx views, mixed k, an
empty-list entry, a single row, independent tensors, CPU tensors, and an offset sub-range — all
identical (/tmp/r4/test_topk_rows.py).

### Result — gain

time --side rollout → /tmp/r4/time_rollout (log /tmp/r4/time_rollout.log):
windows [77.483, 77.520, 78.280] vs [120.215, 116.628, 113.949];
ratios [1.5515, 1.5045, 1.4557]; rollout speedup 1.5039 (was 1.3619 after Round 3).
mismatch_steps empty, layout_problems empty. The windows are also far more uniform than
Round 3's [83.1, 91.5, 83.5], consistent with removing an allocator/GC-driven jitter source.
With Round 3's train 1.3586× this projects a step speedup of ~1.41×.

1.9 hRound 5 — generational GC in the scheduler process (rollout side)
Start 08:44, GPU lock 08:47.
1.9 hHotspot (kind: memory strategy; same host-bound class as Round 4)
_apply_decode_logprobs appends one 128-element Python list per token per request to
req.logprob.output_top_logprobs_val, and output_streamer only *slices* that list (it never
truncates it). At ~8000 response tokens × 31 running requests that is ~500 k live lists and ~32 M
live floats per engine by the end of a rollout. freeze_gc("Scheduler") exists but is only reached
through an explicit FreezeGCReq, which slime never sends, so the default thresholds
(700, 10, 10) keep walking that growing graph.

### Change

In run_scheduler_process, after init and before the event loop: `gc.collect(); gc.freeze();
gc.set_threshold(50_000, 100, 100). Opt-in SGLANG_OPT_TUNE_GC=1`. No values change; only when
cycles are collected. Commit 5804caa (sglang).

### Result — marginal gain, kept

time --side rollout → /tmp/r5/time_rollout (log /tmp/r5/time_rollout.log), finished 09:00:
windows [77.184, 77.348, 77.218] vs Round 4's [77.483, 77.520, 78.280];

The judge's profile only reports GPU kernels, and the rollout is host-bound, so I sampled the
scheduler's Python stacks from outside the process with the image's own py-spy

/tmp/r7/sched_raw.txt). No code path changed and the process was never paused. Top leaf frames:

| share | frame |
|---:|---|
| 57.12% | forward (layers/sampler.py:321) |
| 3.02% | _topk_rows_to_lists (batch_result_processor.py:67) |
| 2.34% | record_batch_in_overlap (scheduler.py:4308) |
| 1.96% | _async_d2h_topk_rows (managers/utils.py:65) |
| 4.47% | get_top_logprobs_raw (logprob_processor.py:108/118/119) |

sampler.py:321 is
if sampling_info.return_top_p_log_probs is not None and bool(sampling_info.return_top_p_log_probs.any().item()):
— a device→host sync on every decode step. return_top_p_log_probs is a device bool tensor
built from a *host* list of per-request custom_params flags, and this recipe runs with
rollout_top_p == 1, so slime never sets the flag (score_centering.py:86 only sets it when
top_p < 1): the tensor is all-False and the sync buys nothing.
It sits inside launch_batch_sample_if_needed → delay_sample_func(), i.e. exactly where the
overlap scheduler is supposed to run ahead of the GPU. Blocking there means the scheduler cannot
prepare or launch step N+1 until the GPU has finished step N's forward *and* sampling.

5.6 hRound 14 — one H2D ordering pair per step instead of one per parameter (train side)
Start 12:27, GPU lock 12:28.

### Hotspot

Round 12's profile: 6.69% of host samples in
param_copy_back_gpu_hook (core/optimizer/cpu_offloading/hybrid_optimizer.py:124), reached from
hybrid_optimizer.py:174 (cpu_optimizer.step(closure)).

Root cause found by reading the code: with --overlap-cpu-optimizer-d2h-h2d,
HybridDeviceOptimizer.build_cpu_optimizer_list creates **one CPU sub-optimizer per parameter
tensor** ("we naively assign each parameter to an individual optimizer"). The copy-back hook is
registered on every one of them, so each step pays, per parameter tensor:
_h2d_stream.wait_stream(current) + torch.cuda.stream(...) + one copy +
_h2d_stream.record_event().wait(current) — two freshly created CUDA events and two stream
waits, ~1000× per rank per step. (This is also why the Adam was so thread-sensitive in Round 10:
_fused_adamw_ is invoked once per tensor, so an OMP parallel region per parameter.)

### Change

MEGATRON_OPT_HOIST_H2D_SYNC=1 →
Megatron-LM/megatron/core/optimizer/cpu_offloading/hybrid_optimizer.py:
step() does wait_stream once before the sub-optimizer loop, runs the loop inside a single
torch.cuda.stream(self._h2d_stream) context, and publishes one event afterwards; the hook then
only issues its copy. Same copies, same order, same stream, and the ordering guarantees are
identical (nothing is enqueued on the compute stream between sub-optimizer steps, and the
compute stream ends up waiting on an event that covers *all* copies rather than the last one).
Guarded by overlap_cpu_optimizer_d2h_h2d so the non-overlap path is untouched.

sub_optimizers, their names, their state and every arithmetic op are unchanged, so the
parameter-record gate sees exactly the same shards. Expected tier: N0 on this change alone.

### Result

time --side train → /tmp/r14/time_train (log /tmp/r14/time_train.log):
train 1.6002×, windows [48.872, 48.15, 49.521] — no gain (Round 10 was 1.6103×; the
difference is inside the window noise). Step-0 mismatch 0.008139924526357157, unchanged.

Conclusion: the 6.69% attributed to the hook is not event/launch overhead — it is the host
blocking inside copy_ while the H2D transfer itself drains. Removing ~2000 CUDA event calls
per step just moved the same wait into the copy. Same lesson as Rounds 2 and 6: a py-spy-hot
line that waits for *real* work is not a lever; only a wait for work that need not happen is.
Switch turned off (MEGATRON_OPT_HOIST_H2D_SYNC removed from the switch file); the code
stays behind its default-off switch, inert.
