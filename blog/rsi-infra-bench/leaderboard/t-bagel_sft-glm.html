1.1 hRound 7 (02:25-...) — BAGEL_FLEX_ATTN: block-sparse flex_attention for the decoder (N1)
- Motivation: attention is ~690 ms of the 2146 ms step (32%): a per-sample SDPA loop with dense
  additive masks (mem-efficient kernel, ~55 TFLOPS effective) over the full L^2 of every sample,
  plus a 7x GQA materialization per layer. The packed batches visit only ~20% of the block pairs
  (cross-sample blocks all masked, cross-split upper blocks masked), so a block-sparse kernel
  should do a fraction of the work.
- The upstream tree already has the whole flex path: the decoder's non-List mask branch runs one
  flex_attention call with enable_gqa over the packed sequence, and Bagel.forward has the
  create_sparse_mask + create_block_mask machinery. It is dead code in this recipe because the
  batch carries dense masks (use_flex=False) and the batch fields are frozen (gate 2 digest).
- New code (behind BAGEL_FLEX_ATTN, default off):
  - _derive_packed_splits (bagel.py): reconstructs each sample's (split_lens, attn_modes) from
    the batch's token layout (vit runs + vit_token_seqlens, vae runs + latent shapes + mse
    positions; text splits are the gaps; a vae span with loss is 'noise'). Verified element-wise:
    reproduces the dataset's dense masks exactly on 92 samples of both data configs, and
    create_sparse_mask over the derived splits equals the dense masks element-wise on 53 more.
  - _build_packed_block_mask (bagel.py): builds the BlockMask directly from the split structure
    in O(seq_len) instead of evaluating the mask over the L^2 grid (upstream's create_block_mask
    compiles a static shape per step with dynamic=False -> one recompile per distinct length; its
    eager path materializes a (1, 32, L, L) bool mask). Visited blocks over-approximate and full
    blocks under-approximate the true visibility (exactly what the flex kernel requires); verified
    against brute-force block truth from the dense masks on 75 samples: 0 missed visible pairs,
    0 wrongly-full pairs, and the persistent mask_mod equals create_sparse_mask element-wise.
  - The mask_mod closes over persistent buffers (allocated once, refilled per step): new tensors
    every step would recompile the flex kernel on their dynamo guards.
  - Fixed padding: torch 2.5's flex template autotuner finds no candidates for symbolic shapes
    (NoValidChoicesError), so the mask and q/k/v are padded to one fixed length, BAGEL_FLEX_LEN
    (default 11520 = the recipe's max_num_tokens, exactly what upstream's data-side flex path
    pads to). The padding sample is causal and isolated, as upstream's pad split.
  - qwen2_navit.py: the MoT flex branch pads to the mask's length (upstream's pad_sequence), and
    BAGEL_FLEX_AUTOTUNE=1 compiles flex_attention with max-autotune-no-cudagraphs.
- GPU smoke test (1 MoT layer, real interleave batch, 28/4 heads): flex output vs SDPA max abs
  diff 1.2e-4 (rel ~5e-3, bf16 kernel difference); backward fine; rerun-identical including in
  deterministic mode (no exception); layer fwd+bwd 27.6 -> 20.2 ms on one batch (flex visits 22%
  of block pairs; full-block fraction 73% after marking noise-span-internal pairs full).
- Judge runs in flight: time (/tmp/r7/time) and check --quick (/tmp/r7/quick) on

1.3 hRound 8 — activation-checkpointing / memory trade (no gain; direction closed)
Start 02:35, end 03:25. Hotspot: the MLP recompute that BAGEL_AC_MODE=mlp still pays
(~108 TFLOP/step of GEMM recompute ≈ 155 ms estimated). AC=none would remove it but needs
more activation memory than AC=mlp keeps freed (measured delta 37.3 GiB).

Probes (judge time, all on the current stack flex+motqkv+logfast):
- AC=none + expandable_segments → ERROR, real OOM: 134.54 GiB allocated (only 308 MiB
  reserved-unallocated, so not fragmentation — genuine capacity). Matches the linear model
  97.18 + 37.3 = 134.5. (/tmp/r8/time)
- AC=mlp:10 (new knob: checkpoint the MLPs of only the first N decoder layers) → 2.3256 s/step
  (1.1194×), peak 125.25 GiB. LESS recompute but SLOWER: per-step times bimodal (1.6–5.3 s) —
  caching-allocator thrash (only ~10 GiB slack under the peak, forced cache releases every step).
  (/tmp/r8b/time)
- AC=mlp:10 + PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True → 2.7818 s/step (0.9359×): ES is
  *worse* here (map/unmap churn, steps 5.4/6.1/6.6 s). (/tmp/r8c/time)
- AC=mlp:16 → 2.0619 s/step (1.2626×), peak 115.55 GiB, steps still spiky (max 4.07 s). (/tmp/r8d/time)

Conclusion: the allocator-pressure knee is below ~110 GiB, where the recompute saving
(≤ 60 ms at mlp:16, ≤ 36 ms at mlp:20) is already eaten by the thrash tax. AC=mlp (all 26
layers) stays. The mlp:<N> knob is kept in the code, default unchanged ("full" = upstream);
submission switches unchanged (AC_MODE=mlp).

Lesson recorded: on this 139.8 GiB GPU with per-step-varying batch shapes, any change that
raises peak allocated above ~110 GiB costs hundreds of ms in allocator churn. Memory headroom
is a performance resource; AC=none-style levers are dead on this machine.
