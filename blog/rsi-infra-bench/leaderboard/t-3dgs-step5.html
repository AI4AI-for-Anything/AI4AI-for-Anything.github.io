0.7 hRound 2 — one fused, bitwise-identical Adam step
- Change (utils/fast_adam.py, new; scene/gaussian_model.py): FusedAdam, a torch.optim.Adam subclass
  whose step() performs exactly upstream's update — the same operations in the same order with the same
  rounding boundaries — in one pass per parameter tensor with a Triton kernel, instead of torch's seven
  _foreach_* passes (lerp_, mul_, addcmul_, sqrt, div_, add_, addcdiv_) that stream the whole parameter set
  through HBM ~18 times instead of 7.
  - Numerics: verified bitwise identical to torch.optim.Adam's foreach path on the six real parameter
    shapes over 7 consecutive steps (/tmp/adamtest.py: torch.equal on p, exp_avg and exp_avg_sq, 42/42 OK).
    The two details that mattered: Triton's / is div.full.f32 (2 ULP) — both divisions must use
    libdevice.div_rn — and sqrt must use libdevice.sqrt_rn.
  - Fallbacks: no triton, or a parameter that is not contiguous / not float32 → the parent's own
    implementation (called through the *unwrapped* Adam.step, see below). A non-contiguous gradient is
    copied (layout only). Parameters without a gradient are skipped, exactly as upstream's Adam does — right
    after a densification the new parameters have no gradient yet and their step is not taken.
  - create_from_pcd: _xyz is created from a transposed numpy view, so upstream's _xyz is a transposed
    (stride (1, N)) tensor for the first 600 iterations; .contiguous() makes it dense from the start
    (values unchanged, per-point shape and dtype unchanged).
- Bug found and fixed while integrating (first attempt was INCORRECT, /tmp/r2b/quick): calling
  super().step() from inside the overridden step() re-enters the global optimizer-step hooks a second
  time, because Optimizer._patch_step_function wraps Adam.step itself as soon as any Adam exists in the
  process (the exposure optimizer does that here). Every fallback therefore counted as an extra
  Gaussian-optimizer step: 24 densification iterations → 24 extra steps, the camera/SH-degree/LR marks all
  shifted by one step. Fixed by calling the original Adam.step (__wrapped__) directly.
  Also fixed: state['step'] is normalised to a Python number (the parent's implementation stores a 0-dim
  CPU tensor), so the fused path can be used after a parent-created state.
- Result: check --quick PASS (exact items of the first 3000 steps match the reference: 3000 renders,
  the same camera order, the same LR/SH-degree marks, the same densification steps, the same dtypes).
  time → 238.698 s, speedup_vs_frozen_reference 1.2819 (windows 68.5 / 87.8 / 82.3 s vs the
  reference's 84.5 / 112.5 / 109.0 s). Peak allocated memory unchanged (5.31 GiB).
  Note: the final Gaussian count is not an exact item; it differs from the frozen record by ~0.1 %, which is
  inside the reference's own run-to-run variation (the rasterizer's backward accumulates with atomics).

1.9 hRound 5 — tried to remove the warp shuffles of `PerGaussianRenderCUDA` (failed, reverted)
Hypothesis: the 11 shfl_up per iteration (and the 14 single-lane global loads they
distribute) were the reason the kernel is latency-bound, and since the forward pass saves the
per-pixel state at every 32-Gaussian boundary, each lane could read its own pixel's state
directly (coalesced) and drop the shuffles. Implemented, built, check --quick PASSED
(steps at which the count changes are robust) but time showed 289.0 s and a peak memory of
6.61 GiB with a final count of 2,274,236 instead of ~1.09 M — the training diverged.
Reason: the shuffled T and ar do not only carry the saved per-pixel state, they carry the
running accumulation across the gaussians of the same bucket at the same pixel; reading the
saved state directly drops the contributions of the gaussians before this lane's in the bucket.
Reverted (comment kept). Re-timed the reverted tree: 226.7 s → 1.3495, peak 5.31 GiB.
Lesson recorded: a rasterizer change must be checked against the record's final count
(~1.09 M at step 3000, ~2.03 M at step 30000, peak ~5.3 GiB), not only against the quick gate.

2.4 hRound 8 — `renderCUDA`: hoist `1 / depth` out of the pixel loop
The forward blending loop evaluated 1.f / depths[collected_id[j]] for every pixel of the
tile, although the value depends only on the gaussian: all 256 threads of a tile issued the
same division (a MUFU.RCP plus its refinement) and the same global load for the same
gaussian. It is now computed once per gaussian while the batch is fetched into shared memory
(collected_invdepth), which removes a division and a load from the inner loop of every
contributing (pixel, gaussian) pair. The multiplication order is unchanged, so the result is
bit for bit what it was.
time 222.47 s → 1.3754 (was 1.3538); check --quick PASS, final count 1,094,037
(reference 1,096,177). Committed as 6197c8d.

### What the remaining time is made of (7.74 ms/step of GPU at N≈2.05 M)

PerGaussianRenderCUDA 2.98 ms and renderCUDA 1.39 ms run at ~100 % of the issue rate (132 SMs
× 4 × 1.98 GHz ≈ 1.05 T inst/s); the fused Adam (0.86 ms) is at the memory roofline; the ATen
ops (0.75 ms) are the same work the reference does, of which 0.17 ms is the irreducible zeroing
of the backward's gradient buffers. The GPU is idle only 0.205 ms/step over 110 kernel launches.

### Directions that did not work, and why

- removing the warp shuffles of PerGaussianRenderCUDA (they carry the per-bucket accumulation
  across gaussians — the training diverges);
- __launch_bounds__ tuning, #pragma unroll, merging guarded blocks, px/py as selects,
  incremental pixf, merging the two early exits (all bitwise identical, all below the timing
  noise — the kernels are at the issue-rate wall);
- two gaussians per thread in the backward preprocessCUDA (the compiler keeps the loop rolled:
  226.7 s vs 222.5 s);
- compacting the radix sort's input with cub::DeviceSelect::Flagged (profiled sort+select+scan
  345 → 225 µs/step, but the extra device→host synchronization needed for the selected count
  drains the pipeline and costs as much as the sort saves: 222.9 s vs 222.5 s);
- fusing the per-gaussian activations (F.normalize) or the L1 loss into Triton kernels: the
  savings are real (~0.5–2 %) but both need a reduction order reproduced bit for bit
  (NormTwoOps accumulates ((0+x0²)+x1²)+x2²)+x3² sequentially, and the L1 mean reduces 1.6 M
  elements with a tree), which is where a mistake would silently become N1.
5.0 hRound 13 — interleave the per-bucket state (kept): 1.39x
PerGaussianRenderCUDA is instruction-throughput bound (measured at 99.5 % of the issue
rate), and of its ~212 instructions per iteration about 35 are the address computation and the
constant-memory reloads for the 14 global loads in the loop.  The forward pass saves the
per-bucket state in five separate arrays (sampled_T, sampled_ar[3], sampled_ard), so the
backward pays five base pointers, five address computations and five parameter reloads per
pixel.

They are now one array of SAMPLE_STRIDE = 6 floats per (bucket, pixel),
[T, ar.r, ar.g, ar.b, ard]: one base pointer and immediate offsets for all five loads.  That
removes eight instructions from the loop body and three pointer parameters from the kernel.

time: 219.57 s / 1.3936 and 220.13 s / 1.3901 on two runs of the same tree, against
221.71 s / 1.3801 before.  check --quick PASS, final count 1093770 (reference 1096177).
Committed as b0f1c07-equivalent (see git log).

The backward reads both with one base pointer and immediate offsets: **sixteen instructions
fewer in the loop body** (528 → 512) and six pointer parameters fewer.
