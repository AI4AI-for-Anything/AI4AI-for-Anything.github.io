3.6 hRound 8 — persistent reductions for the 1536-wide rms-norm (tier N1) *** biggest win so far ***
(start 2026-11-07 05:56 UTC, end 06:19 UTC)

Profile finding (round 6, bench.py profile of the current best tree). The rms-norm reduces over
1536 elements.  Inductor only emits a *persistent* reduction (the whole reduced row stays in
registers) when the reduction is <= 64 elements (1024 for an inner reduction), so it generated a
*split* reduction: the kernel walks the row twice (once to accumulate the sum of squares, once to
apply the scale) and the activation is read from memory twice.

Change. nanochat/inductor_tuning.py (new, off by default, NANOCHAT_PERSISTENT_REDUCTION=1)
patches InductorChoices.should_use_persistent_reduction so that reductions of up to 2048 elements
stay in registers.  Kernels that read or write an fp8 buffer are excluded: a persistent
reduction works on a 1-D tile and the transposed fp8 stores this model needs would be uncoalesced
there (the unfiltered version was a *catastrophic* regression: 1.1049 s/update, speedup 0.9194).
scripts/base_train.py calls apply_persistent_reduction() before the model is compiled.

*Bug found and fixed while implementing this:* SIMDKernelFeatures.buf_accesses is a method,
not a property, and Dep has no .buffer; the fp8 filter has to go through
V.graph.get_buffer(dep.name).get_dtype().  With the bug the filter always raised and silently
disabled the whole switch.

Result. `bench.py time --tree /submission/nanochat --config /tmp/sw/persist.json --out
/tmp/time-persist-2 -> speedup_vs_frozen_reference` 1.0224 (mean), windows 0.9889 / 0.9961 /
0.9955 s/update, per-window ratios 1.0215 / 1.0224 / 1.0235 (min 1.0215).  The benefit bar is
max(1.02, 1 + 2*spread) = 1.02, so the run is now above the bar (was 1.0131 min window).

Tier. N1: the sum of squares of the rms-norm is accumulated in a different order, so the

3.6 hDead end (investigated in round 8, not adopted): fast transposed fp8 stores
The biggest single Triton kernel is the MLP backward glue kernel (65 ms/update, 1407 MB per call at
2.07 TB/s while its neighbours reach 3.9 TB/s).  It writes two *transposed* fp8 buffers (the
column-major copies the weight GEMMs need).  A microbenchmark of the exact generated kernel showed:
* unmodified: 0.485 ms (2.90 TB/s)
* with tl.trans on the value only: 0.357 ms (3.94 TB/s) - **but the data ends up transposed
  twice, i.e. wrong**
* with tl.trans on the value *and* the matching index (correct, bitwise identical): 0.493 ms - no
  gain
* with tl.trans on the index variables: 5.98 ms - catastrophic (Triton materialises the
  transpose of the index tile in shared memory)

Triton cannot express "same logical shape, transposed layout" for a value that comes from an
x-contiguous load while the destination pointer is token-contiguous: the layout conversion that the
store needs is exactly the expensive part, and tl.trans changes the logical shape (which breaks
the data pairing).  Conclusion: with the fp8 layout constraints of torch._scaled_mm (mat1 must be
row-major, mat2 column-major - verified: every other combination raises "Only multiplication of
row-major and column-major matrices is supported by cuBLASLt") the transposed copies are
irreducible, and a fast transposing store is not reachable from Triton's layout system.

4.3 hRound 9: tiled Triton FP8 transpose (N0 candidate) — first attempt was a loss, refined version wins
Profile findings (round 9 start). The judge profile of the current best tree
(/tmp/prof-persist-1, rank 0, 989 ms/update of GPU kernel time) breaks down as
GEMM (cuBLAS nvjet) 452 ms/u, FlashAttention-3 110 ms/u, Triton glue 389 ms/u, NCCL 23 ms/u.
Inside the glue the biggest single kernel is the FP8 gradient kernel that writes the *transposed*
FP8 copy the weight GEMM needs: it reads the bf16 gradient with a transposed (uncoalesced) access
pattern and takes 0.675 ms per call, i.e. ~220 GB/s while its neighbours reach 3.9 TB/s.  The
cuBLASLt FP8 GEMM requires the second operand in column-major layout, so those transposed copies
are unavoidable; only their *cost* is negotiable.

Attempt 1 (regression). A Triton kernel that transposes an already quantized FP8 tensor with a
tiled (tl.trans) transpose reaches 3.0-3.9 TB/s in isolation *and* 3.75 TB/s in situ.  Wiring it
in as a torch.library.custom_op (opaque, so Inductor cannot fuse the quantization into the
transposed store) removed every uncoalesced transposed store from the generated code, but the
judge time run gave speedup 1.0079 (windows 1.0026 / 1.0078 / 1.0129) — a 1.4 % *regression*
versus 1.0224.  Reason (from the profiles): making the copy opaque split the fused kernel, and
Inductor then re-generated the remaining read with a 1-D grid whose index arithmetic
(x % 1536, x // 1536, x % 128, x // 128) costs an integer division per element; the same
read in the 2-D grid version was ~1.9x faster (0.153 -> 0.285 ms/call).

Attempt 2 (adopted). Write *one* custom kernel that reads the bf16 gradient once (coalesced)
and writes both FP8 layouts (row-major for the grad-input GEMM, transposed for the grad-weight
GEMM), the transposed store going through a shared-memory tile transpose.  The scale is computed
with the same expression as _to_fp8 (the amax is order independent, so it is bit-identical), so
the FP8 bytes are unchanged.  The activation's column-major copy uses the plain tiled FP8
transpose.  Microbenchmark: 3.5-3.85 TB/s (0.057 ms for [32768,1536], 0.217 ms for [32768,6144],
1.14 ms for [32768,32768]).

Result (local, 2 GPUs). Loss after updates 0/1: 10.397739 / 10.386679 — bit-identical to the
reference.  Update time 982.6 ms -> 952.2 ms.

Switch: NANOCHAT_FP8_TILED_TRANSPOSE=1 (default off).

What changed. NANOCHAT_FP8_FAST_WEIGHT_REFRESH=1 (default off) replaces the compiled
weight-quantization helper (_quantize_weight_into_compiled: five Inductor kernels plus the

* The FP8 amax of the head's gradient is *not* the amax of the bf16 gradient: Inductor

9.6 hRound 18: the rotary embedding and the QK-norm in dedicated Triton kernels (N1) — 1.1279, full check PASS 1.1263
Profile findings (round-17 tree, /tmp/prof-r18, 3 updates, 916.6 ms/u).  cuBLAS/nvjet FP8
GEMMs 451 ms/u (49 %, 814-1378 TFLOP/s), FlashAttention-3 110 ms/u, the FP8 quantize kernels

the gradient accumulation 10.1 ms/u; the GPU is idle only 3.5 ms/u, so the update is GPU-bound.

Why the rope kernel is slow.  Inductor fuses rms_norm(rope(x)) * 1.2 into one kernel that
reduces over the head dimension (128 elements) with one row per program: the reduction is a
cross-warp reduction for a single 256-byte row, so the kernel moves 600 MB (it also does the
rotation of q *and* k) in 191 us, i.e. 3.2 TB/s where the machine does 4.2 TB/s on a copy.

What changed.  NANOCHAT_FUSED_ROPE_QKNORM=1 (new, off by default) computes the rotation,
the QK-norm and the 1.2 factor with two dedicated Triton kernels (nanochat/rope_qknorm.py,
forward and backward).  They do exactly the arithmetic of the compiled graph - the same fp32
operations, the same libdevice.rsqrt(sum(y^2)/128 + 1.1920928955078125e-07), the same 1.2
factor, the same sum((g*rstd)*(y*1.2)) of the backward, the same fp32 inverse rotation - but
16 rows share one program, so the reduction is a shuffle over a few lanes: 49 us for the
forward (201 MB) and 74 us for the backward (302 MB), i.e. 4.1 TB/s, the roofline.  The
backward recomputes the rotation instead of reading back the rotated values the forward used to
save, so the forward writes half as many bytes.

Numerics (N1).  The sum of squares and the dot product are accumulated in a different order
(the kernel sums the two halves of the head dimension separately), which changes the fp32 rstd
by an ulp: 115 of 50.3 M elements of the forward and 1580 of 50.3 M of the backward differ from
the compiled reference (the bf16 rounding hides the difference on the others).  On a 2-layer D24
model the loss is bitwise identical and only attn.c_proj.weight sees a difference (fp32
noise, 3e-8 on a gradient whose peak is 6e-6).
