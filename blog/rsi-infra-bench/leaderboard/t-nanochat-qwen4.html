### Profile findings (rank 0, 3 steady-state updates, 3.039 s of GPU kernel time = 1.013 s/update)

GPU kernel time ~= wall time, so the GPU is saturated: launch/host overhead is not a bottleneck
(CUDA graphs / reduce-overhead would buy nothing). Accounting per update:

| triton: loss / softmax | 28.7 | 2.8% |

| triton: other | 21.2 | 2.1% |
| eager elementwise / memset / memcpy | 17.7 | 1.7% |
| triton: embedding | 7.9 | 0.8% |

Notable: Inductor already traces into _Float8Matmul (kernel names contain _scaled_mm, clamp,

triton_poi_fused__scaled_mm__to_copy_clamp_clone_mul_pow_reciprocal_relu_t_threshold_backward_view_12
676 us x 96/update = 65 ms/update (6.4%), grid [96,512] block 256, 8 KB shared (tiled fp8 transpose).

FP8 GEMM achieved rate: 5.74e14 FLOP/update/rank over 433 ms = 1326 TFLOP/s vs Hopper FP8 peak 1979
(67%). Backward uses use_fast_accum=False, which on Hopper accumulates at half rate.

### Extra findings that set the direction for later rounds

- The GPUs are power-capped: 700 W limit, ~692 W drawn, SM clock 1455–1485 MHz vs 1980 max.
  FP8 GEMMs achieve ~1300 TFLOP/s against a *throttled* peak of ~1454 → ~89% of achievable.
  FA3 ~578 TFLOP/s bf16 vs throttled ~727 → ~80%. So GEMM and attention are near their practical
  ceiling; the headroom is in the memory-bound glue, and cutting traffic also cuts power.
- Main compute stream is 97.1% busy (2970 ms busy / 3058 ms span over 3 updates). CUDA graphs,
  reduce-overhead and launch-overhead work would buy ~nothing.
- Upstream's num_matmul_params() returns 0 after FP8 conversion (Float8Linear subclasses
  nn.Linear, not nanochat's Linear), so the logged bf16_mfu is meaningless. Real FLOPs/token
  ≈ 4.78e9. Also short_window computes to 512, not the 768 the comment claims.
- Dumping Inductor's code for the same pattern in isolation (/tmp/r2_dump.py) shows the transpose
  *can* be a separate 2D-tiled clone_t kernel; in the real model Inductor instead fuses it into the
  quantize kernel, which is what halves that kernel's bandwidth.

0.5 hRound 2 — keep the fp8 layout transposes out of the quantize fusion
Start ~20:55. Hotspot from round 1: triton: fp8 quant/transpose 221 ms/update, worst kernel
676 us x 96/update = 65 ms/update at 1.79 TB/s while its sibling amax pass runs at 3.95 TB/s.

Change: new nanochat/fp8_transpose.py — a tiled byte transpose (fp8 viewed as uint8, 64x64 tiles,
tl.trans through shared memory) registered as the custom ops nanochat_fp8::transposed_copy and
nanochat_fp8::col_major. Custom ops are opaque to Inductor, so the quantize kernel stays a pure
coalesced pointwise pass and the transpose becomes its own tiled kernel. Switch
NANOCHAT_FP8_TILED_TRANSPOSE=1, off by default. Tier N0: pure data movement, no arithmetic,
no atomics, deterministic by construction.

Verified before timing (/tmp/r2_test.py, under the GPU lock): byte-exact against
x.t().contiguous() for both fp8 dtypes over 7 shapes including non-multiples of the tile; exact
under torch.compile; _scaled_mm accepts the produced layouts and is bitwise equal to the
reference layouts. Caught and fixed a real bug this way: the kernel first returned uint8 instead of
the input's fp8 dtype (the fake impl hid it under compile).

Timing: /tmp/r2-time, PID 299700, log /tmp/r2-time.log, switches /tmp/sw-r2.json
(fast-accum + tiled transpose).

1.8 hRound 6 — split the transpose out of the quantize fusion *only where fusion is the bottleneck*
Round 2's lesson was "do not split a producer from its transposed consumer". The re-localisation above
refines it: that is true for the [32768, 1536] shapes (fusion already at 3.83 TB/s, splitting only adds
a materialisation read) and false for the two heavy-prologue shapes (fusion at 1.79-1.96 TB/s). Round 2
applied the split unconditionally, so the small shapes' losses cancelled the big shapes' gains.

Change: restore nanochat/fp8_transpose.py (tiled 64x64 uint8 transpose, tl.trans, custom op
nanochat_fp8::transposed_copy, exact by construction) and route go_T = go_fp8.t().contiguous()
through it only when numel >= NANOCHAT_FP8_SPLIT_TRANSPOSE_NUMEL. Default 0 = off = upstream.
Tested at 134217728 (2^27), which selects [32768, 6144] (201M) and [32768, 32768] (1074M) and leaves
[32768, 1536] (50M) fused. Tier N0: the transpose moves bytes and the quantize arithmetic is
untouched, so this should be bitwise identical, not merely equivalent.

Predicted from the profile: the 676 us kernel drops to ~259 us (round 2 measured exactly that) plus a
~115 us transpose pass, i.e. ~-30 ms/update from the MLP and ~-3 ms/update from lm_head.

Verified before timing, /tmp/r6_test.py under the GPU lock — ALL OK:
1. tiled transpose byte-exact vs x.t().contiguous() on 14 shape/dtype pairs incl. non-tile-multiples;
2. threshold routing confirmed by call counting (small stays fused, big goes tiled), both byte-exact;
3. _scaled_mm bitwise identical with the tiled operand;
4. Float8Linear forward and weight gradient bitwise identical, switch off vs on, in eager and
   under torch.compile(dynamic=False, fullgraph=True), and compile vs eager.

Timing: /tmp/r6-time, PID 656247, log /tmp/r6-time.log, switches /tmp/sw-r6.json
(validated N1 base + NANOCHAT_FP8_SPLIT_TRANSPOSE_NUMEL=134217728).

### Results

NO GAIN — the autotuner had already captured it. /tmp/r6-time/time.json:
{"status": "ok", "speedup_vs_frozen_reference": 1.0214, "s_per_update": 0.9944} versus the validated
base alone at 1.0203 (0.9955 s/update). The split bought +0.0011, i.e. ~1 ms/update against a
prediction of ~33 ms/update.

The exactness work was not wasted (the change is provably N0 and safe), but the *premise* was stale:

split is applied the fused kernel is no longer the 1.79 TB/s outlier — and splitting then only adds the
extra materialisation read, which is round 2's loss mechanism again.

**Lesson: re-profile the *current best* tree before pricing a kernel-level change. A hotspot measured
on the reference may already be gone after a configuration change.** The switch is left in the tree off
by default (NANOCHAT_FP8_SPLIT_TRANSPOSE_NUMEL=0) and is not part of the submitted configuration.

3.0 hRound 14 — cache the FP8 weight across the grad-accum micro-batches (code rung, N0)
The weight of a Linear is constant across the 4 micro-batches of an update, yet the forward re-quantizes

reference trace the weight-shaped kernels are ~12-14 ms/update (96 attention linears at

13.1 us x 576), plus ~1300 kernel launches whose inter-kernel gaps cost ~1.9 us each. Caching removes
three quarters of both: ~1%+, tier N0 (same values, computed once instead of four times).

- The cache must sit behind a custom op, because a Python dict read inside the compiled region is
  evaluated at trace time and baked into the graph.

  in-place mutation bumps it — add_, mul_, _foreach_add_ and _foreach_copy_ all went 0 -> 1 -> 2

  back (optim.py:426), so no change to the training loop is needed.
- The quantizer inside the custom op is itself @torch.compile(dynamic=False), so it stays fused.
  Running _to_fp8 eagerly would materialise fp32 intermediates and move ~8x the bytes, costing more
  than the caching saves.

7.3 hRound 30 — CUDA graphs: isolate the round-9 segfault and try to route around it
The largest remaining item is the 22.90 ms/update of GPU idle (2.36%) measured in round 29, and
CUDA graphs are the only mechanism that reaches it. Round 9 recorded only "SIGSEGV both ranks after
73 s" with no diagnosis. This round isolates the cause and attempts a surgical fix.

Isolated the culprit with a minimal reproducer. /tmp/r30_cg.py runs one component per process
under TORCHINDUCTOR_CUDAGRAPHS=1, so a crash is attributable:

| stage | component | exit |
|---|---|---|
| 1 | FP8 MLP (Float8Linear -> relu² -> Float8Linear), fwd+bwd | 1 (my test held a graph output across replays) |
| 2 | FA3 alone (flash_attn_func), fwd+bwd | 139 = SIGSEGV |
| 3 | FP8 + FA3 + FP8 | 139 = SIGSEGV |

FA3 is the culprit, not FP8, not _scaled_mm, not the nanochat custom ops (round 9 predates the
weight cache, so the cache was never the cause). PYTHONFAULTHANDLER=1 places the fault at
cudagraph_trees.py:2316 add_function -> cudagraphify — i.e. inside graph *capture*, on the first
call, before any training step.

Found the surgical hook. torch._inductor.config.custom_should_partition_ops (config.py:471,
consumed at scheduler.py:4643-4653) forces a graph partition at a named FallbackKernel, so the
named op runs eager while the rest is captured. config.graph_partition is already default-on in OSS.

Gotcha worth recording: the op names printed by TorchDispatchMode
(flash_attn_3._flash_attn_forward.default, dots) are not what the hook compares against.
scheduler.py uses op.name(), which returns flash_attn_3::_flash_attn_forward — double colon.
With the dotted names the partition silently does not happen and the segfault is unchanged; that cost
one full probe cycle before I printed op.name() directly.

With the correct names the segfault is gone (exit 139 -> exit 1) on both stages, so partitioning
does take effect. It is replaced by a different, harder failure:

```
RuntimeError: These storage data ptrs are not allocated in pool (0, 1) but should be {...}
  cudagraph_trees.py:720 run -> check_memory_pool -> torch._check
```

The eager (uncaptured) FA3 partition allocates its outputs outside the cudagraph private pool, and the
captured partition downstream requires pool-allocated inputs. This is a memory-safety invariant of
cudagraph trees, not a tuning knob.

Decision: stop here, and do not disable the check. The two remaining routes are (a) forcing
graph_break() around every attention call so attention-free graphs are captured separately — which
fragments the whole-model compile at base_train.py:246, destroys the cross-layer fusion that rounds
17/28 showed is already byte-optimal, and costs more than the 2.36% it could recover; or (b) patching
out check_memory_pool, which exists to prevent stale/freed storage being read and would risk silent
numerical corruption. (b) is exactly the kind of safety-check bypass I will not do, and it would
put gate 2/gate 3 at risk for an unmeasurable gain. No code was added to the tree; all work is in
/tmp probes. Nothing committed.

Conclusion: the 22.90 ms of launch latency is not reachable on this stack. CUDA graphs are blocked
by a third-party kernel's incompatibility with capture, and the framework's own partitioning escape
hatch cannot bridge the pool boundary. This closes the last above-noise item in the repriced surface.
