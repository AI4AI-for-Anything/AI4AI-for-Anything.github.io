### Hotspots

1. The text CoT decode loop dominates the rollout. tqdm "Thinking..." runs at **22.3 tok/s
   = 45 ms per decoded token** (196 tokens in the gen round, 384 in the edit round). A 7 B MoT
   decoding 4 tokens needs ~4-5 ms of GPU time (weights only), so the loop is ~10x off the
   memory-bound floor.
2. Cause: host synchronisations. aten::item = 244 157 calls and
   Memcpy DtoH = 262 991 in the two profiled steps. Per decoded token:
   * _static_kv_cache_attention (modeling/bagel/qwen2_navit.py:380,390): 3 device syncs **per
     layer** -> 28 layers x 3 = 84 syncs/token
     ((effective_seqlens + query_lens).max().item(), (query_lens == query_lens[0]).all(),
     query_lens[0].item());
   * Bagel.generate_text_batch (modeling/bagel/bagel.py:1375-1385): 12 .item() per token.
   Every sync drains the GPU queue, so the CPU can never run ahead: the GPU idles while the CPU
   relaunches, and the CPU idles while the GPU runs.
3. Profile table (/tmp/prof-ref/timing_profile.profile.txt): Self CPU 42.2 s vs Self CUDA 27.5 s
   for 2 steps -> CPU/launch bound, with 4.75 s of Command Buffer Full.
   Kernel time: GEMMs 10.3 s (41 %), flash-attn 1.2 s, elementwise/index/copy ~5 s.
4. Diffusion (_forward_flow, 16 gen / 21 edit steps) calls the *readonly* static-KV attention,
   which has 7 more .item() per layer per forward (588 syncs per denoising step).
5. The training part (aten::mm 72 479 calls, record_param_comms 1.55 s NCCL) is ~20 % of the step.

### The remaining synchronisations

The trace shows 184 201 aten::item calls, each with its own Memcpy DtoH, i.e. a
Python loop reading single scalars from the device.  The sweep over the trace shows:

* they are *top level* events (no enclosing torch op) and there is no aten::select
  before them, so they are x.item() on an already 0-dim tensor (not x[i].item());
* they come in bursts of ~8 200/s during the diffusion phase (11.5-24 s of the trace),
  at ~25/s during the decode and not at all during the training phase.

A micro-benchmark (profiled tolist() vs t[i].item()) rules out tolist() (it does one
D2H and no aten::item) and shows that a Python loop of x.item() produces exactly this
signature (aten::item + aten::_local_scalar_dense + one Memcpy DtoH each).

3.0 hRound 5 — the per-token timestep vector (2026-11-07 06:17 → 06:41)
### Profile finding (where the 184 k device syncs came from)

The profile of the current tree (/tmp/prof-cur) showed aten::_local_scalar_dense
184 201 calls in two steps, each with its own Memcpy DtoH — i.e. ~92 k host
synchronisations per RL step (3.9 s of CPU time, 10 % of the 37 s of CPU).

An instrumented probe (a scratch copy of the tree, /tmp/r3-probe2, with
torch.Tensor.item/__float__/__int__/__bool__ counted *by caller*) found the source:

```
942 086  float()   <- modeling/bagel/bagel.py:729/822/926
   8 719  item()    <- torch/optim/optimizer.py:97  (AdamW's step, unavoidable)
      ~1  everything else
```

modeling/bagel/bagel.py builds the per-token timestep of every denoising step with

```python
timestep = torch.tensor([t] * x_t.shape[0], device=x_t.device)
```

where t is a 0-dim CUDA tensor.  torch.tensor on a list of tensors converts
every element to a Python float, so this is one device synchronisation per token
(1026 tokens per image per denoising step, 15–20 denoising steps per round, two
rounds per step => ~150 k synchronisations per RL step, plus ~0.5 M in the step-0
evaluation, which uses the non-SDE generate_image).

### Change (behind BAGEL_FAST_TIMESTEP=1)

modeling/bagel/bagel.py: new helper _timestep_vector(t, n); the three denoising
loops (generate_image, generate_image_sde, generate_image_mix) call it.  With the
switch on it returns t.expand(n).contiguous() — the same float32 values (a
float32 -> double -> float32 round trip is exact), the same dtype and the same
contiguous layout, with no host transfer.  Without the switch the original
expression is used, so the switch is a no-op for the reference.

Checked on the GPU: values, dtype, shape and the resulting timestep embedding
(TimestepEmbedder) are bitwise identical for n = 1, 2, 3, 1024, 4098, and
unique() still sees a single value (the assert in _forward_flow).

### Change (behind BAGEL_CUDA_GRAPH_DECODE=1)

modeling/bagel/bagel.py: the rollout text decode of generate_text_batch is
replayed from a CUDA graph:

* one graph per shape (num_active, the set of still-active cache rows); only the
  token ids and the position ids change from step to step, and both are written
  into static input buffers before the replay;
* the KV-cache lengths are read from the device *inside* the graph
  (flash_attn_with_kvcache takes cache_seqlens as a device tensor), so the
  replay attends over exactly the same keys as the eager step;
* the graph is captured by hand (CUDAGraph.capture_begin/capture_end) instead of
  with the torch.cuda.graph context manager, because that manager empties the
  caching allocator before every capture, which changed the block layout the
  (memory hungry) training phase sees — with it the run died with an OOM in the
  training backward;
* every graph gets its own memory pool and the graphs are deleted at the end of
  the rollout, so the pool is back in the allocator before the training phase;
* modeling/bagel/qwen2_navit.py: Qwen2ForCausalLM.forward_inference and
  Qwen2Model.forward_inference take the host mirror of selected_cache_indices
  (selected_cache_indices_host) so that the capture does not have to read the
  indices back from the device.

Anything unexpected during the capture (an unsupported op, a synchronisation, ...)
falls back to the eager path, which computes exactly the same values.

### Validation

On a scratch tree with a small randomly initialised BAGEL (/tmp/test_graph_rng.py,
4 layers, 4 sequences):

* the generated token ids and the returned probabilities are bitwise identical
  to the eager path (same sha256);
* the CUDA generator's offset advances by exactly the same amount (68) with and
  without the graph — the decode forward itself consumes no RNG, only
  torch.multinomial does, and that stays outside the graph;
* the captured step is 3.7x faster than the eager step on that small model.

The advantage and all_gather phases are where the ranks wait for each other: they vary

So the step time is rollout + reward service + training, and the *reward service* is on the

there.

### Change — overlap the reward service with the batch preparation

The reward requests are submitted at the end of the rollout, so the service is busy for ~2.6 s
while the CPU waits for the responses.  The work that does not need the rewards is moved in
front of that wait:

* train/rollout_controller.py: pack_batch/pack_iterator can now *defer* the advantages --
  the batch is packed with placeholders and the slots are remembered
  (fill_deferred_advantages fills them with the very same values once the rewards are there).
* train/online_rl.py: the packing and the reference-model forward (which only depends on the
  packed batch, not on the advantages) now run *before* the reward wait; the training loop uses
  the batch and the reference log-probs that were prepared there.

The random draws keep their order (the reference model's randn_like is still the first draw
after the rollout, the policy model's the second), the collectives keep their order on both
process groups, and the advantages that end up in the batch are the same numbers as before.

The muls are mostly the rotary position embedding: in the generation branch

### Change

modeling/bagel/qwen2_navit.py (BAGEL_FAST_ROPE=1): a Triton kernel that

8.3 hRound 14 -- the fused RMSNorm of the inference path (2026-11-07 11:30 -> 12:05)
### Where the time goes

The profile of the two profiled steps (/tmp/prof-3) shows that the
normalisation is the largest remaining non-GEMM cost: aten::mul 2.03 s of
self CUDA time (7.9 %), aten::pow 0.35 s, aten::mean 0.37 s, the
reciprocal square root 0.10 s and a large part of the 1.07 s of aten::copy_
come from the RMSNorm.  The eager Qwen2RMSNorm walks over the activation
tensor six times (to(float32), pow(2), mean(-1), rsqrt, the scaling
multiply and the weight multiply).  There are about 12000 normalisations per
step, almost all of them on the 4096 vae tokens of the diffusion rollout.

### Change

modeling/qwen2/fast_rmsnorm.py (new) and modeling/qwen2/modeling_qwen2.py
(BAGEL_FAST_NORM=1): the normalisation of the inference path (the rollout
and the frozen reference model, i.e. everything that runs without grad) is
done by two Triton kernels: one that computes the sum of the squares of every
row and one that applies the weight and the scaling.

The kernel reproduces the reduction order of aten::mean exactly, which is
the only way to keep the result bitwise identical:

* aten::mean reduces the last dimension of a contiguous float32 tensor with
  one warp per row (blockDim.x == 32) and combines the 32 lanes with the
  shfl_down tree over the offsets 1, 2, 4, 8, 16,
* for a row of 128 elements lane t owns the elements t, t+32, t+64, t+96,
  for a row of 3584 elements the loads are vectorised and lane t owns the
  elements 4*(t+32*m)+j,
* the squares are rounded to float32 *before* they are added and the adds are
  emitted as add.rn.f32 / mul.rn.f32 inline assembly, so that the
  compiler cannot contract them into an fma (which would round only once),
* the 32 lane partials are combined with the same butterfly
  (reshape/split), the mean's factor (rows / (rows * width) in float32)
  and the reciprocal square root are still computed by aten.

The eager path is kept for everything that needs a backward pass and for the
layouts the kernel does not cover.
