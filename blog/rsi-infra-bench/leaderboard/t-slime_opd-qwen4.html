### Correction to the Round-1 note on offload

launch.sh passes no --offload-train/--offload-rollout, but slime/utils/arguments.py:2135-2146
defaults both to True under --colocate. So the colocated dance does happen: sleep 3.0–3.4 s
and wake_up 1.5 s per step (slime timers), and the student engines' 0.45 static fraction is
released while the trainer runs. That leaves roughly 143 − 36 (teacher) − 31 (Megatron) ≈ 76 GB per
GPU for activations in the *full* loop, which is what makes OPD_RECOMPUTE=none worth screening.

### Rollout: investigated, no change yet
Decode is weight-bandwidth bound: 4.54 ms of GPU kernel time per step at bs=32 per engine
(~4950 tok/s), of which the nvjet GEMMs are ~2.85 ms ≈ 59 % of the 4.8 TB/s peak. The remaining
~1.9 ms/step is GPU idle. Attributing the idle gaps in the rollout trace to Python frames puts
them in decode_cuda_graph_runner.load_batch (223 ms/200 steps), process_batch_result_decode
(222 ms), prepare_for_decode/alloc_for_decode (163 ms) — scheduler bookkeeping, not kernels.
num_continuous_decode_steps, the knob that would amortize exactly this, is declared in
srt/arg_groups/fields/schedule.py but never read anywhere in this sglang tree, so it is dead.
The sampler's full-vocab fp32 passes (div_ by temperature 1, softmax, log) are only ~0.19 ms
of the 4.54 ms, so they are not worth the numerics risk. No rollout change submitted so far;
OPD_STUDENT_SGLANG_ARGS (commit c22526a5) is the hook for screening engine args if a lever turns up.

2.4 hRound 6 — micro-batch packing (02:06 → …)
The step runs 64 micro-batches for 64 samples: max_tokens_per_gpu 4096 × cp 2 = an 8192-token
bin, and a sample is ~8300 tokens (8135 response + prompt), so first_fit_pack
(slime/utils/dp_schedule.py:120) puts every sample in a bin of its own — the documented
"individual sample larger than the cap" exception. Every micro-batch therefore pays the full
per-micro-batch Python/launch/grad-accumulation cost for one sample's worth of GEMMs.

Packing is semantically free here. loss.py:1623-1629 scales the loss by
num_microbatches / step_global_batch_size * dp_world_size(with_context_parallel=True), which
cancels Megatron's 1/num_microbatches and the 1/dp_cp gradient scale. The step's gradient is
Σ_samples (Σ_tokens x·mask / sample_mask_sum) / 64 for *any* binning. get_sum_of_sample_mean
(cp_utils.py:54) also derives each sample's CP zigzag split from that sample's own
total_length, not from the bin, so the CP chunk boundaries do not move either. Only GEMM shapes

Directly attacks the measured 1.25 s/step. OPD_GC_FREEZE=1

### The design that keeps the forward exact

Every per-head operation in the GDN — the projections' rows, the depthwise conv's channels, the
chunk scan, the gated RMSNorm (which normalises over head_v_dim, i.e. *within* a head) — is
independent across heads. So a rank computing 16 of the 32 heads produces bit-for-bit what the
replicated path produces for those heads. The only place heads meet is out_proj, which reduces
over all num_v_heads * head_v_dim columns.

Round 4 sliced out_proj too and summed two bf16 partials with an all-reduce — two extra roundings
per layer, compounding over 24 layers, which is what produced its 2 % grad_norm error. This version
instead re-gathers the heads along the last dim before out_proj
(gather_from_tensor_model_parallel_region, whose backward splits), so that GEMM keeps the
reference's full-width reduction and its single rounding. The layer output is therefore still
replicated and the SP scatter is untouched; only the *input gradient* is partial, and it is summed
by switching the SP gather's backward from split to reduce-scatter (tensor_parallel_output_grad).

Sharded parameters are marked param.sequence_parallel = True so Megatron's
finalize_model_grads sums their gradients over TP. out_proj.weight is deliberately excluded:
it still runs full-width, its gradient is already replicated, and summing it would double it. The
wrapper's input_layernorm.weight is included, because its output gradient is the sharded GDN's
partial input gradient.
