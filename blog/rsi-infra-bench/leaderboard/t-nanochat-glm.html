1.1 hRound 1 — FP8 weight-quantization cache (NANOCHAT_FP8_WCACHE)
- Start/end: 2026-11-06 ~15:10 – 16:45 UTC.
- Profile first (judge profile, /tmp/prof-ref-1, reference tree): per update, the FP8
  "glue" around the 6 converted linears is eager ops inside the opaque _Float8Matmul, and the
  weight quantization is recomputed on every one of the 4 micro-batches in *both* directions:
  forward quantize chains (amax→scale→mul→clamp→cast) plus backward recomputes writing row- and
  col-major, ≈16–20 ms/update across the 24 layers, vs. weights only changing in optimizer.step().
  Also noted: grad_weight GEMMs (K=32768) run at 144 CTAs vs 132 SMs (wave quantization) — the
  target of Round 2.
- Change: nanochat/fp8.py — persistent per-Float8Linear buffers _w_fp8 (row-major e4m3),
  _w_fp8_t (col-major e4m3), _w_qinv (f32), filled by refresh_fp8_weight_caches(model) once
  per update from the training loop (scripts/base_train.py, top of the step, before the
  micro-batches; the weights are final there). The compiled path (_Float8MatmulCached) reads the
  buffers instead of re-quantizing per call; eager calls (judge's eval, sampling) keep the
  reference path. The refresh reproduces Inductor's quantize arithmetic bitwise (f64 reciprocal →
  f32 scale, clamp, cast; verified against the generated kernel source). Switch
  NANOCHAT_FP8_WCACHE, default off.
- Bugs found and fixed while validating: the first version refreshed from a post-step hook in
  MuonAdamW.step() that was never registered → stale caches from update 1 (first quick check
  /tmp/check-r1-quick: loss frozen at 10.39, all 175 params differ from update 1). Fixed by
  moving the refresh into the training loop top (nanochat/optim.py reverted to upstream).
- Result (check --quick, /tmp/check-r1-quick2): status NOT_BITWISE, exact_items_ok
  true, rows/updates/hyper-parameters all identical. 4 params differ at update 0 (c_proj weights
  h.2/13/17/…), all 175 from update 1 (the 4 ULP-level perturbations compound). Per-update losses
  match the reference record run to ≤2e-4 over 10 updates (10.397737 identical at step 0;
  9.847431 vs 9.847258 at step 8) — healthy trajectory, far below seed noise σ≈0.023.
- Why not bitwise (investigated to root cause): the reference's AOTAutograd backward does not
  save the fp8 input tensors for attn.c_proj/mlp.c_proj; it recomputes their input
  quantization (amax over the FA3 output / relu output) inside backward kernels whose reduction
  order differs from the forward's amax → ~1 ULP scale differences → ~16 differing fp8 bytes per
  tensor → grad_weight differs by ~1e-9 (measured: /tmp/grad_cmp_result.log, 48 c_proj weights,
  0.6–1.5 % of elements, maxabs ≲1.5e-8; qkv/fc/lm_head grads bitwise identical). My version saves
  the forward's quantization (cheaper) and cannot reproduce Inductor's fused recompute reduction
  order. Inherent N1 — same class as the judge's accepted reduction-order control tree.

- time: run in progress → /tmp/time-r1 (result appended below).

1.7 hRound 4 (continued) — CUDA graphs dead end; prefetching loader
- CUDA graphs attempt (NANOCHAT_CUDA_GRAPHS=1 → torch.compile(mode="reduce-overhead"),
  same kernels, N0): the timing run SIGSEGVs on both ranks (/tmp/time-r4-cg, status ERROR).
  FA3/cuBLAS workspaces under graph capture are not stable in this setup. Reverted; the lever is
  dead (also note gate 1 invalidates runs where CUDA graphs are "requested but skipped", so this
  lever was all-or-nothing from the start).
- Prefetching loader (NANOCHAT_LOADER_SLOTS, nanochat/dataloader.py, default 0 = upstream):
  the profile showed the gaps are the loader's own work (rustbpe encode + best-fit packing,
  ~19 ms/batch, untraced by the profiler) landing at chunk boundaries. New opt-in variant
  _prefetched_bos_bestfit: a worker thread produces the byte-identical batches (packing
  logic copied verbatim) into a pool of N slot buffers; next() pops a finished batch and clones
  it out of the slot. Slot reuse is made explicitly safe: the consumer records a CUDA event after
  its clone and hands the slot back; the worker blocks on that event before refilling the slot
  (so both the slot's pinned staging buffer and device buffer are provably idle when reused).
  The free-slot handoff bounds the worker to N batches ahead — tokenization and parquet
  row-group bursts disappear from the critical path. Verified byte-identical against the
  synchronous loader over 12 batches (first version had a slot-reuse race caught by the test at
  batch 6 — fixed by the event-after-clone handoff; also noted rustbpe's encode is not safe to
  run concurrently from two threads, which only ever happens if two loaders run at once — the
  recipe runs one).

2.9 hRound 6 conclusion → Round 7 direction
The remaining big non-roofline block is ~330 ms/update of Inductor Triton glue (clones 176.7 +
casts/norms 154.8) at ~1.5 TB/s with heuristic kernel configs. The graph/fusion plan itself
is good — what's suboptimal is the per-kernel config choice (block sizes, num_warps,
vectorization). torch.compile(mode="max-autotune-no-cudagraphs") tunes exactly that without
touching the plan: pointwise kernels and max-reductions (amax) produce identical values under
any config; only reduction-order rounding (norms, CE) can differ — N1-class, same tier as
concat which passed gate 3 at 0.41σ. Pure config lever, no code change: NANOCHAT_COMPILE_MODE.

3.7 hRound 8 conclusion — loader_slots marginal; spike root cause found
- NANOCHAT_LOADER_SLOTS=4 on top of concat=2 + autotune: /tmp/time-r8-ls —
  1.0237 (windows 1.0039/1.0203/1.0220, ratios 1.0318/1.0202/1.0195, smallest

  moves the loader off the chunk boundary but its GIL-held work still stalls the training
  thread's kernel launches.
- Root cause measurement (CPU-only, frozen assets, /tmp/loader_cost.py): parquet row
  groups are 1024 rows; read_row_group 10.1 ms, to_pylist 4.0 ms — cheap. The expensive
  part is rustbpe encode + the packing loop: ~6.5 encode calls of 128 docs per update
  (~60–80 ms/update of loader CPU), and at document-buffer refills the worker runs up to 8
  back-to-back encodes with no packing in between — a near-continuous GIL-held burst exactly
  at the rg transitions (u17/u20/u27/u28/u32 where the spikes live, both trees). The
  training thread has ~0 slack (GPU ~1.0 s/update vs wall ~1.0 s), so any worker GIL time is
  a direct stall; the reference is frozen with its own +1.5–2 % spikes, so removing mine is
  pure ratio.
- Conclusion: threads cannot fix this (shared GIL). Next: a forked child process that owns
  read + encode + packing (own GIL); the parent only receives packed rows over a pipe.
4.1 hRound 9 — process-based loader (NANOCHAT_LOADER_PROC, default off)

5.9 hRound 10 — profile the spikes: root cause found and fixed (loader H2D copy blocks the training stream)
- profile --from 14 --iters 8 → /tmp/prof-r10 (updates 14–21, rank 0, trace
  timing_profile.trace.json, 89 MB chrome trace).
- The spikes are GPU idle, not slower kernels. Per update: GPU busy is flat
  969–980 ms while wall goes 1005→1164 ms; idle grows 31.6 → 30.9 → 49.0 → 63.9 →
  60.1 → 74.5 → 193.5 ms. Kernel-time diffs between the 3 slowest and 3 fastest
  updates are noise (±2.5 ms). u20 alone has a 131 ms gap.
- Inside every big gap the host issued zero kernel launches and no aten ops —
  it was blocked, not working. The one 131 ms gap sits inside Optimizer.step and
  ends exactly when step returns.
- **The blocker: 16 × cudaStreamSynchronize of 140–187 ms on the training
  stream** — exactly 2 per update, inside aten::copy_ ops that each end with a
  512 KB Memcpy HtoD (Pageable -> Device) followed by the consumer's clones.
  That is the proc loader's produce thread staging gpu_buffers[slot].copy_(cpu_buffers[slot]):
  when the CUDA runtime does not treat the source as pinned it synchronizes the
  copy's stream before returning — and on the training stream that wait is the
  entire enqueued backlog (~150 ms of forward/backward). The producer therefore
  paced the consumer 1:1 (2 of its 4 copies/update block during the backwards,
  2 return instantly at the drained boundaries — matching the 16 blocking copies),
  the 4-slot queue ran dry at every micro-batch boundary, and the GPU idled
  ~9 ms (floor) to 131 ms (spike updates) waiting for the next batch.
- Isolated reproductions (no GPU contention for the lock, tiny scripts):
  side-thread copy_(pinned, non_blocking=True) with a busy stream: 0.15 ms;
  same with a pageable source: 318.8 ms. Connection.recv releases the GIL
  (refuted as the cause); upstream base_train already disables GC after step 0
  (refuted); power/clocks were refuted in Round 9.
- Fix (commit da86ca6, tier N0): staging runs on a dedicated torch.cuda.Stream()
  (empty, so the runtime's synchronize is a no-op) with staged_events[slot]
  recorded on it; the consumer's default stream waits that event before cloning.
  Yields bitwise identical to the sync path (batches 0–3 + state dicts); fetch
  latency under an 80 ms GPU backlog 4–23 ms → 0.06–0.32 ms; no
  cudaStreamSynchronize in a profiled fetch loop. Same mechanics available for
  the (off-by-default) NANOCHAT_LOADER_SLOTS path if ever needed.
- Expectation: windows 2–3 lose their ~13–18 ms/update of boundary idle; if the
