5.1 hRound 14 — expensive lever: custom skinny bf16 GEMM for decode (rollout). Negative result, no code shipped.
- sglang already has a Hopper bf16 GEMV (--bf16-gemm-backend gemv), but it only handles m == 1 (bs=1) and some N ranges. Decode runs m = 32 per engine, so it does not apply. A CUDA-core GEMV cannot serve m = 32 (about 32 FLOP per weight byte, compute-bound on CUDA cores), so tensor cores are required.
- Development microbenchmark (not a score; kernel selection only), M = 32, Triton tl.dot with fp32 accumulation, bf16 output, skinny tiles, 2 032-config sweep on the two MLP shapes:
  - gate_up (N = 12 288, K = 4 096, 101 MB): cuBLAS 29.8 µs (3.4 TB/s); best Triton 28.6 µs (4 % better).
  - down (N = 4 096, K = 6 144, 50 MB): cuBLAS 17.1 µs (2.8 TB/s); best Triton 19.7 µs (slower).
  - qkv-like (N = 5 120, K = 4 096): cuBLAS 11.0 µs already at 3.8 TB/s.
- Conclusion: cuBLAS is already within about 70–80 % of DRAM bandwidth on these shapes; a Triton replacement gains at most a few percent on the GEMMs (about 0.1 ms per step, roughly 1 s per rollout), so it is not worth shipping. Correctness of the kernel was fine (relative error ≈ 1e-4 on M ≤ 32).

7.6 hRound 21 — Megatron tensor-parallel communication overlap: the bootstrap is fixed; the userbuffer shape is the next blocker
- Root cause of the earlier assertion (intra_domain_group.getBackendType() == backend): slime's patched torch.distributed.new_group returns a ReloadableProcessGroup wrapper for the groups that Transformer Engine's initialize_ub creates (its world group), and the C++ CommOverlapHelper cannot read a wrapper's backend. Fix tested: create TE's groups with the unwrapped new_group (temporarily restore the original function around Megatron's _initialize_tp_communicators call). Initialization then passes.
- New blocker in the first training step: copy_into_buffer: _ubufs[_tp_id].numel() == input_size fails. Transformer Engine sizes the userbuffers once, from seq_length × micro_batch_size / cp, and our packed micro-batches have variable token counts. Overlap therefore needs every micro-batch padded to one fixed length (a data-path change in slime's batching).
- Estimate: overlap could hide about 60–70 % of the 21 % of GPU time in tensor-parallel collectives (≈ 5–8 % of the train step), but padding to a fixed length costs ≈ 2–3 % (samples are 8.2–8.7 K tokens). Net ≈ 2–4 % of the train step. Not pursued now; changes reverted (commit history unchanged).
7.9 hRound 22 — optimizer offload fraction 0.5 re-examined: the regression is the sleep backup of GPU-resident optimizer state
- time --side train with fraction 0.5 (/tmp/r21/off05): windows 57.81 / 62.34 / 59.13 s (speedup 1.08). Steady-state py-spy of rank 0 (/tmp/r21/off05_stacks.raw, 11 380 samples): torch_memory_saver pause 27 % and resume 8 % of samples, against ≈ 3 % and ≈ 1 % in the all-CPU baseline.
- Cause: slime sets TMS_INIT_ENABLE_CPU_BACKUP=1, so every allocation that is not explicitly excluded is backed up to host memory at sleep and restored at wake. The GPU-resident half of the optimizer state (≈ 27 GB) is therefore copied to host and back every RL step, which costs more than the CPU Adam it saves.
- Keeping that state resident would need it outside the memory saver. Training-phase memory is the limit: full resident state (≈ 54 GB) would not fit beside the training peak, and the half-resident version adds OOM risk to the final evaluation for about 2 % of the loop. Not pursued; reverted.
