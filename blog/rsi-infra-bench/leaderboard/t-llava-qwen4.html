5.7 hRound 12 — sequence packing: skip padding in ALL decoder GEMMs (N1, big win) (08:13–09:05)
The expensive lever the earlier "ceiling" call missed. Re-profile of gc18 over 3 steps
(/tmp/r12/profile) with shape recording exposed the padding fraction: the collator right-pads
each micro-batch to its longest sample, and flash-attention already skips padding (varlen), but every
decoder projection / MLP GEMM still runs on the full padded (16, seq, 4096):

| step | padded bs×seq | valid N (flash-varlen) | padding |
|---|---|---|---|
| A | 16×1113=17808 | 13600 | 23.6% |
| B | 16×1353=21648 | 14724 | 32.0% |
| C | 16×1134=18144 | 13694 | 24.5% |

So ~27% of the dominant ~59% GEMM work was wasted on padding, plus 138 per-layer unpad/pad gather
copies. LLAVA_OPT_PACK_SEQ (off by default) gathers valid tokens once into a packed (1, N, hid)
batch at LlamaModel.forward input, runs all 32 layers on it with a single shared cu_seqlens
(LlamaFlashAttention2._flash_attention_forward → direct flash_attn_varlen_func, no per-layer
unpad), then scatters back to (bs, seq, hid) so the sparse-loss path is untouched. Under causal
attention + right padding, padding tokens never influence valid tokens, so the valid-token math and
the loss are unchanged; only GEMM shapes/rounding differ (N1). Reuses the existing layer/MLP/norm/GC
path verbatim. Bug fixed mid-round: the no-padding fallback first tested max_seqlen==seq, which is
*always* true (the longest sample defines seq) → switched to min(seqlens)==seq.

Screens (/tmp/r12/time_pack*): pack+gc18 = 1528 ms (1.787x), alloc 122.5→91.45 GiB (freed
~31 GiB). That headroom lets GC skip ALL layers: pack+gc32 (no recompute) = 1368 ms (1.996x),
reserved 123.25 GiB (~17 GiB margin). The packed RoPE then fell back to eager (non-arange positions),
showing ~112 ms generic elementwise + ~29 ms BUnary in the profile; added a fused varlen RoPE
(flash_attn.ops.triton.rotary.apply_rotary with cu_seqlens, conjugate backward; guarded to
right-padding so packed position == position-within-sequence) → pack+gc32+fused-rope = **1284 ms
(2.126x)**, reserved 123 GiB.

9.8 hRound 22 — custom fused Triton AdamW optimizer kernel (N1, ADOPTED, +3.4%) (12:30–13:08)
Corrects an unmeasured dismissal (and round 21's "optimizer tail near floor" claim). Last turn I
called a custom fused-Adam kernel "disproportionate risk for ~2% uncertain gain" *without measuring it*
— exactly the assumption error the persistence feedback warns against. The mandate forced measuring it;
it gave the biggest single gain since packing.

Investigation: the recipe uses optim="adamw_torch" and zero3.json has no optimizer section, so
deepspeed_init → trainer.create_optimizer() builds torch.optim.AdamW (not DeepSpeed FusedAdam),
with zero_allow_untested_optimizer=True. Its CUDA foreach path (_multi_tensor_adamw) is NOT one
fused kernel but a *sequence* of foreach ops — lerp_/mul_/addcmul_/sqrt/div_/add_/addcdiv_ —
each re-reading and writing the full fp32 master buffers (~60–80 bytes/elem of HBM traffic). The
optimizer step is a serial tail after backward (not overlapped), so this traffic is exposed wall time.

- First attempt — force torch's fused=True (_fused_adamw_, single kernel): crashed,
  RuntimeError: ... two devices, cuda:1 and cpu ... state_steps. torch fused AdamW requires CUDA
  state_steps (capturable mode); this optimizer uses CPU state_steps. Incompatible without capturable.
- Adopted — custom Triton fused AdamW: one kernel streams g/p/m/v once, writes p/m/v once
  (28 bytes/elem, ~2.7× less traffic). Math matches torch's non-capturable foreach path exactly:
  increment step first, bc1=1-β1^t, bc2=1-β2^t, m=β1·m+(1-β1)·g, v=β2·v+(1-β2)·g²,
  p-=(lr/bc1)·m/(√v/√bc2+ε) (fp32 accumulation; only op-rounding order differs → N1). Hook: wrap
  torch.optim.adamw.adamw dispatcher; unsupported cases (amsgrad/maximize/weight-decay/complex/
  tensor-lr/grad_scale/capturable/differentiable) fall back to the original. LLAVA_OPT_FUSED_ADAM,
  off by default. BLOCK=2048, num_warps=8.
- Screens /tmp/r22/time_fadam{,_triton,_re}: 1228.5 / 1227.1 ms (2.2233 / 2.2257x), reserved
  ~126 GiB, problems:[], first-loss 1.3833 identical to baseline (step2 1.2873 identical).
