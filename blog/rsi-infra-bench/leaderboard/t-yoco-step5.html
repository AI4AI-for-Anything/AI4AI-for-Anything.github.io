YOCO_NO_SHARD=1 (in /submission/switches.json). Off by default.

goes full-per-rank (12.8 GB master + 25.6 GB Adam) — fits in 144 GB.

### Bottom line
The reference is well-optimised; the tractable wins are the three "remove work the recipe doesn't need"
changes above (13.0%, all N0). Everything else is at a hardware floor (GEMM/all-reduce/Adam/MP copies) or
locked behind custom ops (compile) or forbidden (QKV/FFN weight fusion changes param names = gate-2 exact
item; fp16 Adam stats = removing fp32 optimizer state). The remaining soft target (~27 ms of
autograd-dispatched model copies) needs a bespoke kernel and is high-effort/low-reward/N1-risky, so it was
not pursued in favour of keeping the verified N0 13.0%.
1.7 hAlso screened & rejected (round 5, cheap)
- YOCO_FLATTEN=1 (force flattened fp32 master so the two mixed-precision copies become one contiguous
  copy each): FusedAdamV2 *does* support flat params, but upstream hard-codes flatten=False for bf16, the
  flatten path is a per-device dict layout that is risky to force, and the copies are already
  bandwidth-bound (per-param vs flat is the same bytes) so the win is only ~launch overhead (~0.6%).
  Not worth the layout risk. Not implemented.
1.9 hDecisive finding (round 6): the step is GPU-bound, so fusing the small ops cannot help
A microbenchmark made RMSNorm look expensive (0.34 ms/call fwd+bwd × ~67 calls ≈ 22 ms). But re-running
the RMSNorm torch.compile under the profiler shows the inductor kernels do appear (4 triton_
kernels) while the elementwise/reduce/memcpy/cast totals are unchanged (132.0/19.3/198.3 ms vs
132.7/19.2/199.0). Interpretation: the many small ops are **CPU-dispatch-bound and that dispatch is
hidden behind the GPU** (host ≈ GPU time, zero inter-kernel gaps in the trace). A fused kernel has the
same GPU bytes (the fp32 intermediates stay in L2), so it removes CPU launches — which are already
overlapped — and cannot reduce wall time. This is *why* every compile variant returned ~0. The only
levers that moved the needle were the ones that removed GPU work (the OSS broadcast, the DDP bucket
copies, the grad-zero fill). The GPU side is now at its floor, so the tractable optimisation space is
exhausted at the verified N0 13.0%.

3.9 hRound 19 — WIN: compute the clip's L2 norm on the bf16 grads before the fp32 sync (N0, +~0.3%)
Upstream's clip_grad_norm syncs bf16->fp32 *first*, then norms the fp32 master grads (12.8 GB read).
bf16->fp32 is lossless and apex's multi_tensor_l2norm accumulates in fp32, so norming the bf16 grads is
bitwise identical while reading half the bytes. Proof: (a) op-level microbenchmark — raw bytes equal;
(b) the compare report against the reference is byte-identical to the apex-only stack's (sha256
6478de81...), i.e. zero additional numerical difference, so gate 3 passes identically. Op-level saving
612 us/update. time: 1.2233 vs the 1.222 baseline (positive, within noise). Gated by YOCO_NORM_ON_BF16.
Commit 66cfb1d.
4.0 hRound 20 — "Adam reads bf16 grads" closed (apex forbids it)
Same order-questioning lens applied to the biggest remaining memory item: the Adam reads the fp32 grad
(12.8 GB) that the sync just wrote. If apex FusedAdam could take the bf16 grads directly it would
cast internally (lossless) and read half the bytes (~1.9 ms). But apex's step raises on an explicit
grads argument ("FusedAdam has been updated. Simply initialize it identically to torch.optim.Adam, and

6.3 hRound 56 — fused Triton AdamW + bf16 write: **+6.6%** (1.2427 -> 1.3232, PASS)
The round-54/55 "drift" was NOT Triton arithmetic. Probing apex with a uniform element
(m=1, g=1) showed the *formula* was wrong: the 1.3e-4 drift concentrated on near-zero-gradient
elements whose update is eps-dominated, and apex's real denominator is sqrt(eas)/sqrt(bc2) + eps
with step_size = lr/bc1 — i.e. the sqrt(bc2) sits in the denominator *together with eps*, NOT on
the whole update (which is what rescaled eps by sqrt(bc2) too). With that fixed the kernel is
bitwise identical to apex on the master weights and the bf16 model weights over 200 updates
(0 of 3.4e9 elements differ; only exp_avg/exp_avg_sq differ by ~1e-7, and that never propagates
into the weights, so the loss trajectory is identical). Tier N1 only because the moments are not
bitwise — the tree was already N1 from the compiled loss.

Implementation: one Triton launch covers all 239 parameters through a pointer-array +
binary-search grid, because a per-parameter launch costs ~63 us of dispatch here
(239 x 63 us = 15 ms, more than the saving). It replaces apex's multi-tensor AdamW AND the
separate fp32->bf16 sync: 28 ms instead of 39 ms (measured at full 3.4B-parameter scale; the
kernel is at ~3.6 TB/s, apex's own multi-tensor path only reaches ~2.6 TB/s).

Two integration traps, both found the hard way and both worth remembering:
1. Wrapping bench.py in flock deadlocks it — it takes the GPU lock itself and the inherited
   lock fd blocks its own acquisition. (The task statement says not to wrap it; the symptom is a
   process with ~4 s of CPU and no children.)
2. The optimizer to patch is fairseq.optim.fused_adam.FusedAdamV2 (bf16 -> adam_v2=True),
   not apex.optimizers.FusedAdam — FusedAdamV2 has its own step. And the patch must keep
   fp32_optimizer.step() on the call path: the judge counts iterations with a *global
   optimizer-step post hook*, so bypassing the optimizer object silently makes every run
   "incomplete". Fixed by re-wrapping the replacement in torch's profile_hook_step.

7.0 hRound 57 — fuse the whole grad path into the Adam kernel: **+7.3%** (1.3165 -> 1.42, PASS)

Numerics are exact rather than approximate: the kernel computes
g = float(bf16 grad) * clip_coef and stores that as the fp32 master grad, which is
precisely what the lossless bf16->fp32 copy followed by mul_ produces.  Verified
bitwise against fairseq's real FusedAdamV2 over 60 updates on the real parameter
structure: 0 differing elements in the fp32 master grads, the masters, the bf16
weights and exp_avg.

Two non-obvious things this needed:
  * fairseq's grad-norm buffer is a DoubleTensor, so the clip coefficient is a
    float64 0-dim tensor.  Tensor.mul_ with a 0-dim operand keeps the fp32
    gradient dtype (it casts the scalar to float first), so reading the fp32 cast is
    bitwise what the reference computes -- and it is the only form Triton 2.3.1 can
    compile (it asserts on an f64 -> f32 truncating store).  Verified bitwise.
  * _multiply_factor must be cleared after the step, as the reference does inside
    _unscale_grads, or the clip coefficient compounds across updates.

The first attempt of this round failed gate 3 badly (all six endpoints 500-3500
sigma off, master grads ~2650x too large) and the cause is worth remembering:
DDP re-creates the gradient bucket views on every backward -- it double buffers
them, so the live grad alternates between two buffers.  Caching the bf16 gradient
list on the fp16 optimizer made the kernel read the previous update's buffer, i.e.
memory the allocator had already reused.  A standalone correctness test with fixed
tensors cannot catch this; only the real run does.  Fixed by re-reading the live
gradients every step (~100 us of Python, invisible against 165 ms), and diagnosed
with a one-shot stderr probe comparing the live and cached data_ptr.

7.5 hRound 58 — deferring the grad sync past the clip: **REJECTED** (1.5222 but INCORRECT)
The fused AdamW kernel writes the fp32 master gradients itself, so the
_sync_fp16_grads_to_fp32() that the fp16 optimizer's clip path still ran after
computing the norm looked redundant — a ~20 GB pass over 239 copy launches.
Deferring it past the clip measured 1.5222 (154.3 ms/update), but the full
check returned INCORRECT on an exact item, not on numerics:

    cross_rank_pattern  model=master kind=grad sync=local
    reference_equal_fraction 0.0   candidate_equal_fraction 1.0

The numerics adapter records grad/master.<param> from its pre-step hook,
which sits inside fp32_optimizer.step() and takes each rank's slice of the

gradient view was wrong.  Recorded as a trap: **the fp32 master gradients must be
populated before the optimizer step, because the judge reads them there.**

8.2 hRound 61 — skip the model-parallel mappings at model_parallel_size == 1:
+0.7% (1.4837 -> 1.4875, PASS)

The host is a co-bottleneck, and the biggest host-side item that can actually be
removed is not an aten op but autograd graph size: copy_to_model_parallel_region
and reduce_from_model_parallel_region are torch.autograd.Functions whose
forward returns their input unchanged and whose backward is the identity at
model-parallel world size 1, yet each still costs one graph node per Linear layer
-- 185 nodes per update in forward and the same again in backward.  Returning the
input directly is the same computation bitwise (same tensors in, same gradients
out, no RNG use), so this is tier N0.

The world size is read lazily -- at the first Linear forward, by which point
initialize_model_parallel has run -- and cached; if it cannot be read, or is not
1, the mappings stay, so a multi-model-parallel run is untouched.

9.9 hRound 64 — skip DDP's post-all-reduce gradient division (N1, 1.4762 -> 1.5017, PASS)
Found the largest attributable non-floor item by mining the trace's kernel
names: the two MulFunctor<float> elementwise kernels totalling 8.75 ms/update
are DDP's reducer::mul_out — the pass that divides every gradient bucket by the
world size after the all-reduce.  Their element counts add up to 3.6 B, i.e. the
whole gradient set, and the bucket sizes match DDP's 50 MB cap (plus one 616 MB
bucket each for the embedding and output-projection weights, which exceed it).

Registering a DDP comm hook makes DDP skip that C++ pass entirely — verified
directly with a 2-rank probe: without the hook the gradient is the mean, with it
the sum.  The gradients therefore arrive world-size times larger, which must be
compensated in two places or the *clip regime* changes:
  * the clip norm is halved, so the clip coefficient is unchanged.  Without this
    the coefficient would halve too, and for 1.0 < gnorm <= 2.0 the reference
    does not clip while this would — a ~5% gradient error;
  * the scale the fused kernel applies is halved.
Both are exact to ~1 ULP (halving bf16/fp32 by a power of two is exact; the only
residual is the 1e-6 in the clip formula).
