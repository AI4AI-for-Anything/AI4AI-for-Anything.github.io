1.6 hRound 4 (08:46-09:00 UTC) — the student's log-prob forward pass (train side)
Hotspot: the separate log-prob forward pass (9.9 s/step = 6.4 % of the step). It exists because the
OPD advantage needs the student's log-probs *before* the training forward.
The OPD advantage is base_advantage - opd_kl_coef * (student_logp - teacher_logp), and with GRPO
(get_grpo_returns = per-sample reward broadcast) and no --normalize-advantages, the base advantage
does not depend on the student's log-probs at all. So the penalty can be applied inside the training
loss with the log-probs the training forward just computed -- the same values (same logits, same
kernel) that the separate pass produces.
Change (slime, commit 672a012): loss.py gets apply_opd_kl_to_advantages_in_loss; actor.py skips
the separate log-prob pass when the conditions hold (behind OPD_REUSE_LOGPROBS_IN_LOSS=1).
Numerics: step 0's train/loss = 0.05341373383998871 and train_rollout_logprob_abs_diff =
0.008052160032093525 are bitwise identical to the reference's; step 1 differs only by the
reference's own run-to-run noise (the reference is not bitwise repeatable).

2.8 hRound 8 (10:20 UTC) — the student's decode: a device-to-host sync in the sampler
Profile of the student's sglang worker (bench.py profile --side rollout, /tmp/r3/profile): the decode
window (198 steps, bs=32) has the GPU busy only 40.7% of the time; the host spends 8.7 ms between
steps. The cause: one aten::item per decode step inside Sampler.forward
(sglang/srt/layers/sampler.py: bool(sampling_info.return_top_p_log_probs.any().item()), 199 calls,
781 ms of the 2.27 s window, each one a device-to-host sync). It blocks the host until the whole forward
has finished on the device, so the GPU idles while the host prepares the next step: the decode is
host-bound, not device-bound.
Change (sglang, switch OPD_SAMPLER_NO_SYNC, off by default): the per-request "return top-p log-probs"
flags are already known on the host when the batch is built, so the batch carries a host-side flag
(need_return_top_p_log_probs) and the sampler asks the question without touching the device. The answer
is identical (the device tensor is built from the same host list), so the sampling, the tokens and the
log-probabilities do not change; only the synchronization disappears.

4.5 hRound 10 results (12:00-12:35 UTC) — the GPU-idle overhead around the training step
Diagnostics (1 Hz nvidia-smi utilization poll next to the judge's own time --side train, /tmp/r10):
the training step itself is GPU-bound (95-100 % utilization on all four GPUs during the forward /
recompute / backward), but every step has a ~12 s GPU-idle window: the sleep (4.2 s) + the wake_up
(1.4 s) + the CPU-offloaded optimizer (~7 s). The per-phase timers of the reference show the same shape.
Two candidate cuts were measured:
1. Skip the host-memory release in the sleep (clear_memory(clear_host_memory=True) ends in
   malloc_trim(0) over a multi-hundred-GB heap): change (slime, switch OPD_SKIP_HOST_CLEAR, off by
   default) -> time --side train /tmp/r10/time_train_hc: windows 53.55 / 55.22 / 55.21 s, train side
   1.3123x vs the baseline's 55.25 / 53.84 / 52.60 s (1.3407x) and the sleep times unchanged
   (4.2 / 4.1 / 6.3 / 4.0 / 4.4 / 4.5 / 4.1 s). => No effect; reverted (the trim is not the cost).
2. The CPU optimizer is at the host-memory roofline: measured on this box, a 1e9-parameter Adam-like
   chain (lerp_ + mul_/addcmul_ + sqrt + addcdiv_) costs 380 ms, i.e. 179 GB/s of host traffic - the same
   190 GB/s that a plain add_ reaches. The optimizer moves ~68 bytes per parameter per step
   (master + 2 moments + grads) over 4.5 B parameters per GPU, i.e. ~1.2 TB per step at 175 GB/s = the
   measured ~7 s. A fused kernel would remove the denominator temporary (-24 % of the traffic, ~1.7 s) and
   keeping the moments on the GPU is impossible in the colocated memory budget (the peak would go from
   105 GB to ~129 GB, which round 9 showed is catastrophic). => No safe win; the optimizer stays.
Other measured facts of this round:
- The engines' offload/onload (the KV cache + the CUDA graphs + the weights, released to the host and
  re-allocated every step) costs ~2.4 s of the step. Keeping the engines' weights on the GPU would save
  ~0.9 s but raises the training-phase peak by 9 GB (105 -> 114 GB of 140 GB), which is too close to the
  regime where round 9's variant collapsed. => Rejected.
- The teacher's prefill chunking is the only sanctioned teacher lever that does not change its kernels
  (a different GDN prefill backend would move the linear-attention state at every chunk, i.e. far beyond
  the reference's own re-batching spread). Best measured: `--chunked-prefill-size 32768
  --max-prefill-tokens 32768` (the teacher side 1.0907x vs 1.058x for chunk 16384) -> now in
  /submission/switches.json; worth ~0.45 s of the ~114 s step.

6.4 hRound 15 (13:55 UTC) — CUDA MPS: can the teacher overlap the student's decode?
Where the rollout's 57.6 s goes (from the judge's own records of the r8 run, /tmp/r8/time/rollout_tree/judge):
- the 64 samples are generated in 41.6 s (the first one at 32.7 s into the rollout, the last at 41.6 s);
- the teacher's answers all arrive at 57.6 s -> a tail of 16.0 s after the last generation;
- the teacher alone (replay mode) needs 16.6 s of GPU time for the same 525 k tokens.
So the teacher's scoring is a *serial tail*: the requests only exist once a sample is finished (the first
one at 32.7 s), so at best ~9 s of the teacher's work could hide under the student's decode.
Two ways to overlap: (a) make the teacher cheaper (the prefill is compute bound at 40 % MFU; the chunk
size sweep above shows nothing there), (b) let the teacher's kernels and the student's kernels run on the
GPU *at the same time* - the student's decode is memory bound (the GEMMs run at 2.9 of the 3.2 TB/s
read bandwidth) and the teacher's prefill is compute bound, so they use different resources.
Without MPS the two processes take turns on the GPU (context time slicing); with MPS their kernels run
concurrently in one server context per GPU.
Pre-checks on this box (cheap, no full run):
- nvidia-cuda-mps-control -d works here; the daemon starts and the clients connect (the control log
  shows NEW CLIENT / NEW SERVER).
- NCCL works under MPS (a 2-rank allreduce gives the right values, twice, with a sleep in between) -
  this matters because sglang's TP2 and Megatron's collectives are NCCL.
- torch_memory_saver (the Megatron offload) works under MPS (region/pause/resume OK) - it needs the
  LD_PRELOAD hook, exactly as slime sets it.
- a synthetic memory-bound + compute-bound pair on one GPU: the wall time is already ~= the compute-bound
  time without MPS (0.557 s vs 0.53 s alone) and 0.542 s with MPS -> the gain from MPS on this pair is
  small, so the real measurement decides.
Change (sglang, commit pending): sglang/srt/mps.py + a call in launch_server.py that starts the MPS
daemon when CUDA_MPS_PIPE_DIRECTORY is set (off by default; nothing else changes, the same kernels run).
The teacher server is the first process of a run (bench/launch.sh starts it before slime), so the daemon is
up before any CUDA context exists and every later process (the rollout engines, Megatron) joins it.

Why MPS cannot help here (the analysis that led to the experiment):
- the student's decode is memory bound: the profile shows the decode GEMMs moving 9 GB of weights per
  step per GPU at ~2.9 of the 3.2 TB/s read bandwidth this box measures, i.e. ~90 % of the roofline;
- the teacher's prefill is compute bound (27 B params, 2 FLOP/param/token, ~31 k token/s over 4 GPUs =
  ~420 TFLOP/s per GPU = ~42 % MFU);
- but the two do not overlap in the first place: the response lengths are 1947..8192 with a median of
  8192, so almost all 64 samples finish within the last ~2 s of the 42 s decode. The teacher's requests
  therefore only exist in the last few seconds and its 16.6 s of prefill is a serial tail after the
  students are done (measured: the last sample's generation ends 12.6-16.0 s before the rollout ends).
- so the teacher's tail cannot be hidden under the student's decode; it can only be made cheaper
  (the prefill chunking, swept in round 14) or the samples would have to exist earlier (they cannot).
