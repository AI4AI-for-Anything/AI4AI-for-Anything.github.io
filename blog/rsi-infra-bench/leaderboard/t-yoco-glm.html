1.6 hRound 2 (2026-11-06 18:10–18:50): pipelining the Adam step with the shard exchange (YOCO_FAST_PIPE)
Profile after round 1 (/tmp/r2/profile, 5 updates, rank 0): per-update kernel time ≈ 1.11 s
instrumented; gemm 65.7 ms, nccl 50.8 ms (DDP all-reduce 31.7 ms mostly overlapped + OSS exchange
19.1 ms fully serialized after the Adam step), memcpy/cast 43.8 ms, elementwise 26.3 ms, optimizer
multi_tensor (Adam) 18.3 ms. The optimizer section is still Adam (18.3) + exchange (18.6) back to
back = ~37 ms with zero overlap — the round's hotspot.

Change: YOCO_FAST_PIPE=K in yoco/models/_fast_optim.py — pipelined OSS.step. The local
shard is split into K=8 near-equal param-aligned chunks; the inner fused Adam takes one step
over K param groups (fairseq's FusedAdamV2.step launches one multi_tensor_adam multi-tensor
kernel set per group), and each chunk's all_to_all exchange is issued right after that group's
kernels are enqueued — from a wrapper around fairseq's module-global multi_tensor_applier — so
exchange k overlaps Adam chunk k+1 (NCCL waits at enqueue for the current stream's pending writes
to the exchange input; the K exchanges serialize on NCCL's stream and the last .wait() covers
all). Tier N0: same per-element Adam math over the same tensors (bitwise whatever the grouping),
same bytes exchanged, group step advances by exactly 1.

Two failures found and fixed before any valid timing:
1. First design stepped the inner Adam K times per update. The judge's timing harness counts
   updates with torch's global optimizer-step post hook — "the first optimizer object that ever
   steps defines the iteration (in the reference the shard-local FusedAdam inside fairscale's
   OSS; one step per update)" (bench/timing.py). With 8 inner steps/update the timer counted 8
   "iterations" per update: time returned ERROR ("the random-number stream differs from the
   reference from update 1 on"), bogus 7.24× / 0.0323 s-per-update, windows of 10 chunks ≈ 1.25
   real updates, StopTiming after 3 updates (other_optimizer_steps [3], window_range 0.62).
   The judge defines an update as one FusedAdam step, so the redesign above keeps exactly one
   inner step per update. (torch.optim.Optimizer._patch_step_function wraps the class's step
   at first instantiation, so the patched OSS.step and the inner FusedAdamV2.step each still
   fire the hook once per update, in the reference order: other_optimizer_steps [24] again.)
2. Rank-1 split sizes flipped in the rewrite (`RuntimeError: Split sizes doesn't match total
   dim 0 size`): the output tensor is the *other* rank's bucket slice (n_other elements), so
   output_split_sizes must be [n_other, 0], input_split_sizes [n_mine, 0]. Fixed.

3.2 hRound 5 — fused multi-tensor cast copy (YOCO_FAST_CASTCOPY)
Start 2026-11-06 20:06, end 2026-11-06 20:25. Hotspot from the fresh profile
(/tmp/r5/profile): memcpy/cast 25.4 ms/update — the fp32↔bf16 gradient/weight syncs.
torch._foreach_copy_ has no fast path for mixed dtypes: it silently falls back to one
unvectorized per-tensor kernel per parameter (measured: identical time and launch count to
an explicit per-tensor loop, ~33x off the HBM roofline for the cast traffic).

Change (_fast_optim.py, switch YOCO_FAST_CASTCOPY=1): one fused Triton kernel per
copy list. Program pid copies BLOCK contiguous elements of segment block_seg[pid] at
offset block_off[pid] (block layout cached per size list); tensors are passed as int64
pointer tables (tl.load(...).to(tl.pointer_type(...)), verified supported in triton 2.3).
bf16→fp32 is exact; fp32→bf16 is cvt.rn like torch's copy_ (proven bitwise in the RMSNorm
work). Elementwise → deterministic; guards fall back to foreach for anything but
contiguous CUDA tensors of the expected dtypes.

Rejected in-round: YOCO_FAST_SKIPWSYNC (skip the fp32→bf16 refresh of the non-owned
half). The A/B caught it: loss matched updates 1–2 then diverged. My invariant was wrong —
each rank's fp32 masters are ALL live: own shard ← Adam, other shard ← the OSS exchange
every update, so the reference's full refresh is semantically required (only the non-shard
fp32 *gradients* are dead, which is what round 3's SHARDGRADS correctly skips). Removed.

Correctness evidence: unit bitwise suite /tmp/r5/castcopy_test.py (mixed sizes, odd
