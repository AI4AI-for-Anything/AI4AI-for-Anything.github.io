4.4 hRound 14 — the full check of round 13 FAILED the statistical gate: the fused Adam was not bit-exact
Start: 2026-11-09 10:45 UTC. End: 2026-11-09 11:20 UTC.

The full check of the round-13 tree (/tmp/r14c/check/check.json) came back INCORRECT: gate 2
(exact items) passed, gate 3 failed with SSIM -5.58 sigma, LPIPS +3.55 sigma, PSNR -2.09 sigma.
No full check had ever been run before (rounds 1-13 only ran check --quick, which compares the
exact items and not the trained model), so the culprit could be any of the changes, not only the last
three.

### Diagnosis (cheap probes instead of 5-minute N1 runs)
* The judge's reference record (bench/records/ref.json) has the number of Gaussians after 3,000
  steps: 1,092,971 (the bootstrap run of the reference gave 1,095,412, so the run-to-run spread of
  the *count* is ~0.2 %). The candidate gave 1,056,479 (-3.3 %): a systematic difference, not noise.
* A probe that runs the tree's own entry for 3,000 steps takes 20 s, so the switches could be bisected
  with it: without switches 1,094,119, GS_VECTOR_STATS=1 1,094,136, GS_ASYNC_LOSS=1 1,096,426,
  GS_FUSED_ADAM=1 1,053,183. The fused Adam was the culprit; the CUDA changes (rounds 5, 11, 12,
  13) are fine.
* torch.norm over a strided view and over a gathered copy is bit-identical (checked), so the
  vectorised densification statistics are not the problem either.

### Root cause
create_from_pcd builds the positions with torch.tensor(np.asarray(pcd.points)), which keeps the
strides of the numpy array: self._xyz is column-major, i.e. not contiguous. The fused Adam
kernel walks the parameter, the gradient and the optimizer state as flat buffers, so for the whole
training (the positions only become contiguous at the first densification, iteration 600) it wrote
the update of the first Gaussian into the first elements of the buffer and left the other positions
untouched: the position update was simply wrong. Torch's own Adam uses the foreach route, which
respects the layout, which is why the reference is right.

### Fix (commit ba310c4)
FusedAdam.step uses the fused kernel only when the parameter and the two state tensors are
contiguous, and otherwise falls back to the operations of torch.optim.Adam (lerp_,
mul_+addcmul_, sqrt/div/add, addcdiv_) - the same operations the reference runs, so the
values are the same. The fallback is only used for the first 600 iterations.

### Verification
* The parameters of the first steps are now identical to the ones of the torch.optim.Adam path
  (only the last-bit differences of the rasterizer's atomics remain).
* The number of Gaussians after 3,000 steps: 1,093,883 with the fused Adam, against 1,093,831 and
  1,095,026 for two runs of the reference path (the broken version: 1,053,183).

6.7 hRound 20 — the tight tile box
Start: 2026-11-09 12:35 UTC. End: 2026-11-09 13:01 UTC.

Profile of the steady state (bench.py profile --from 7010 --iters 20, /tmp/r23/profile):
5.36 ms of GPU time per iteration. The binning (duplicateWithKeys 1.05 ms + the radix sort
0.26 ms) and the two render kernels (1.20 + 0.58 ms) are the hot spots.

A Gaussian is rasterized against every tile of its 3-sigma square, but the square is
the bounding box of the *largest* principal axis in both directions. The tiles that can
change the image are the ones overlapping the ellipse of the pixels whose alpha is at least
1/255 (q <= log(255*opacity)), whose axis-aligned bounding box is
sqrt(2k*cov_xx) x sqrt(2k*cov_yy) - much tighter for an elongated Gaussian. Every tile
that is dropped this way contains only pixels with alpha < 1/255, which the render kernel
skips anyway, so the image is unchanged; the tile rectangles are stored per Gaussian
(int2* rects) and used by both the preprocess and the binning kernel.

6.7 hRound 21 — one warp per Gaussian in the binning kernel
Start: 2026-11-09 13:09 UTC. End: 2026-11-09 13:35 UTC.

7.3 hRound 22 - the depth path of the rasterizer and the exponential of the rejected pairs
Start: 2026-11-09 13:40 UTC. End: 2026-11-09 14:12 UTC.

Profile of the tree at the start of the round (/tmp/r26/profile, 4.76 ms of GPU
time per iteration): rasterizer backward 1.85 ms (39 %), rasterizer forward 1.47 ms
(31 %), fused Adam 0.70 ms (15 %), the torch ops of the loop 0.72 ms (15 %).
The CPU runs at about the same rate as the GPU (the wall clock is 5.14 ms per
iteration), so every percent of GPU time is a percent of the wall clock.

Two changes, both inside the rasterizer:

1. The exponential of the rejected pairs (alpha_power_threshold in
   auxiliary.h). The alpha of a (Gaussian, pixel) pair is
   min(0.99, opacity * exp(power)) and the pair is skipped when it is below
   1/255, that is when power < -log(255 * opacity). The exponential is the most
   expensive part of that test and most of the pixels of the tiles a Gaussian
   touches fail it, so the threshold is now computed once per Gaussian and the
   power is compared with it *before* the exponential is evaluated. The margin
   (0.01) makes the test conservative: every pair that passes it is still tested
   exactly as before, so the set of accepted pairs - and therefore the image - does
   not change. The forward kernel got 5 % faster (578 -> 550 us in the profile of
   /tmp/r27/profile); in the backward kernel the test did not pay off (the inner
   loop is register bound), so it was left out there.
2. The depth path of the rasterizer is now switched off when the depth
   regularization is inactive, which is the case of the recipe (--depths "", so
   no camera has a depth map). The rasterizer then does not compute the inverse
   depth of the image, does not carry the inverse depth of the buckets through the
   sampled state, and does not evaluate the depth part of the gradients (the
   gradient of the depth image is exactly zero when the depth is not used, so the
   gradients are unchanged). The flag travels from train.py (the condition of
   the depth regularization) through gaussian_renderer.render and the rasterizer
   settings into the four kernels that touch the depth. The per-Gaussian gradient
   buffer of the inverse depth is not even allocated any more.

  against 1.976 before.
* check --quick (/tmp/r29/quick): PASS (the exact items of the first 3,000
  steps are identical).
* Numerics: N0 (the image and all the gradients are bit for bit the same).
* An earlier attempt at the same round (/tmp/r27) put the exponential test into

8.4 hRound 23 - the spherical harmonics gradient, written in a contiguous way
Start: 2026-11-09 15:00 UTC. End: 2026-11-09 15:16 UTC.

Profile of the tree at the start of the round (/tmp/r32/profile, 4.61 ms of GPU
time per iteration): rasterizer backward 1.06 ms (23 %), rasterizer forward 0.52 ms
(11 %), the fused Adam 0.65 ms (14 %), the backward preprocessCUDA 0.49 ms
(10.5 %), the binning kernel 0.45 ms (10 %), the radix sort 0.26 ms (6 %), the
device memsets 0.15 ms (3 %), the torch ops of the loop about 0.60 ms (13 %).

The hotspot of the round is the backward preprocessCUDA. It computes, for every
Gaussian, the gradient of the loss with respect to its 15 spherical harmonics
coefficients, and writes it to the buffer of shape [P][15][3] that the optimizer
reads. The buffer gives every Gaussian 180 bytes, so the 45 floats of a Gaussian
are contiguous but the Gaussians of a warp are 180 bytes apart: the 45 stores of
a thread touch 45 different cache lines, and the 45 stores of the 32 threads of a
warp touch 1440 of them. The stores of the warp use 12 % of the bandwidth they
move.

The gradients are now staged in the shared memory of the block and written to the
global buffer by the block at the end of the kernel, in the order the buffer uses:
the 45 floats of the Gaussians of a block are then written by the 32 threads of a
warp one after the other, so the stores are contiguous. The staging costs 45
shared stores and 45 shared loads per thread, and it replaces 1440 cache line
transactions per warp by 135. The buffer is not zeroed any more, because the
kernel fills every element of it (the Gaussians that are not visible get a zero
gradient, as before).

The values are the ones the old code computed: computeColorFromSH is unchanged
except for the place where it writes its result, so the arithmetic, and the way
the compiler contracts it, are the same. This was checked with a test program
(/tmp/shgx) that runs the old and the new preprocessCUDA on the same random
data and compares the 2,250,000 floats of the gradient buffer: **0 of them
differ**.

* time (/tmp/r36/time): 2.2058 (138.08 s), against 2.0559 before.
* check --quick (/tmp/r35/quick): PASS (the exact items of the first 3,000
  steps are identical).
* Numerics: N0 (the gradient buffer is bit for bit the same).
* A first attempt at this round put the computation of the gradients in a

8.8 hRound 24 - the normalisation of the quaternions, in one kernel
The profile of the tree at the start of the round (/tmp/r37/profile, 4.86 ms of
GPU time per iteration over the window 7,000..7,019) put the composite op
torch.nn.functional.normalize(self._rotation, dim=1) at about 0.29 ms of the
iteration, that is 6 % of it. It is not one kernel but eight: the norm is
reduced twice (once in the forward, once again in the backward of the norm, as
torch recomputes it), the sum of the four squares is a reduction over the
broadcast dimension of the division, and the rest are elementwise passes over
the quaternions and their gradients. In the trace the two reductions of the
norm cost 77 us per iteration, the reduction of the division 48 us, and the
elementwise passes about 150 us more.

The normalisation is now a single CUDA kernel per direction
(submodules/diff-gaussian-rasterization/quat_normalize.cu, behind the
GS_FUSED_NORMALIZE switch), which computes the norm, the divisor and the
result, and in the backward the whole chain of the gradient.

The arithmetic is the one of torch, operation by operation and rounding by
rounding, and it was measured before writing the kernel:

* the norm is sqrt((q0*q0 + q1*q1) + (q2*q2 + q3*q3)); the four squares are
  summed in pairs, which is what the reduction of linalg_vector_norm does on
  this shape (the sequential sum differs from it on 12 % of the samples);
* the divisor is max(n, 1e-12), and the result is q / d;
* the backward is u_k = (q_k/d)/d, t_k = -g_k * u_k,
  gd = (t0+t1) + (t2+t3), gn = (n >= eps) ? gd : 0,
  gx_k = (g_k/d) + gn*(q_k/n); the sum of the four t_k is again in pairs,
  and the product gn*(q_k/n) is formed as it is written above and not as
  (gn*q_k)/n (which differs on 17 % of the samples);
* a zero norm is replaced by one before the division by the norm, as torch does
  in the backward of the norm, so that the gradient of a zero quaternion is
  zero and not a NaN.

The kernel uses __fmul_rn, __fadd_rn, __fdiv_rn and __fsqrt_rn, so that
the compiler cannot contract the operations into fused multiply-adds, which
would round differently.

The comparison with torch over about 30 million quaternions (random ones, ones
over ten scales from 1e-8 to 1e30, heavy-tailed ones, and the edge cases: the
zero quaternion, the ones whose norm is exactly the epsilon, the infinite and
the NaN ones) gives 0 differences in the forward and 0 differences in
the backward, and the NaNs land on the same elements (/tmp/normtest).

* time (/tmp/r38/time): 2.396 (127.12 s), against 2.2058 before.
* check --quick (/tmp/r38/quick): PASS (the exact items of the first
  3,000 steps are identical).
* Numerics: N0 (the forward and the backward are bit for bit the ones of
  torch).
9.6 hRound 25 - two experiments on the backward render (no gain, reverted)
The backward render (PerGaussianRenderCUDA, 1081 us per iteration, 26 % of the
time) is the biggest kernel of the iteration.  Two changes were tried on it, both
measured with bench.py profile (the time of the kernel is in the profile):

1. The alpha log-threshold pre-filter.  The forward render skips the
   exponential of a pair whose contribution to the tile is below 1/255 (it
   compares the power with log(1/(255*opacity))).  The same test was added to
   the backward render, before the exponential.  The backward render went from
   1059 us to 1068 us: the backward is not bound by the exponential (its
   last_contributor early exit already removes most of the pairs, and the warp
   divergence prevents the lanes from skipping the test), so the extra
   comparison only costs.
2. The pix_grad4 load moved after the alpha test.  The backward render
   loads the state of the pixel it works on before it knows whether the pair
   contributes.  Deferring the load made it slower (1081 us).

Both changes were reverted (git checkout).  The threshold itself was proved
safe (0 violations over 16 million samples, /tmp/normtest/thr.py), it simply
buys nothing.
9.6 hRound 26 - the occupancy of the backward render (a wash)
The backward render uses 56 registers (nvcc -Xptxas -v) and was launched with
one warp per block, so that the number of resident warps per multiprocessor was
limited by the hardware limit of 32 blocks per multiprocessor and not by the
registers: 32 warps out of the 64 a multiprocessor can hold.

The kernel does not care how many warps share a block (it computes the bucket
index from the warp index), so the launch was made configurable
(GS_BWD_WARPS, off by default, cuda_rasterizer/backward.cu): with four warps
per block the limit becomes the number of registers, 36 warps.
