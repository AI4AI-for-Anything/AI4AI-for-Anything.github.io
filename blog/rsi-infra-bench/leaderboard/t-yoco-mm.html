Findings (from the Chrome trace, one update = 266 ms under the profiler):

* The GPU is essentially never idle (largest gap 2.2 ms) -> the update is GPU-bound, not
  data- or launch-bound.
* NCCL is 41% of the kernel time. 595 AllReduce_Sum_bf16 (DDP gradient all-reduce,
  119 calls/update, 47.5 ms/update) and 10 Broadcast_RING_LL (fairscale ZeRO-1 master-weight
  broadcast, 2 calls/update, 191.7 ms total = 38.3 ms/update).
* The ZeRO-1 broadcast is fully serial: fairscale::oss::refresh_trainable (23.5 ms/update) is
  preceded by a cudaDeviceSynchronize (23.3 ms) and is followed by a 44.7 ms
  cudaStreamSynchronize at the end of the update -> the broadcast is on the critical path.
* The copy traffic of the fp32 master weights: memset of the master grads (13.8 GiB), bf16->fp32
  grad copy (20.7 GiB), clip-coefficient multiply of the master grads (27.6 GiB), fp32->bf16
  weight copy (20.7 GiB) = ~83 GiB of memory traffic per update, all of it avoidable or fusable.
* The GEMMs run at ~575 TFLOP/s (the output projection at 787 TFLOP/s) -> there is little to win
  in the model's matmuls.
* aten::item syncs: 4 per update, all of them waiting for the GPU (the longest is the 44.7 ms
  one at the end of the update).

Conclusion: attack (1) the optimizer's inter-rank communication, (2) the master-weight copy
traffic, (3) the gradient all-reduce's efficiency. The model's matmuls and attention are fine.
0.2 hRound 2 — replicated Adam (no ZeRO-1 broadcast)
yoco/models/optim_overrides.py (new, imported by models/__init__.py), three switches, all off
by default:

* YOCO_OPT_REPLICATED_ADAM=1: replaces fairscale's ZeRO-1 wrapper with a variant that keeps the
  Adam state of every parameter on every rank and drops the per-step broadcast (and the device
  synchronize in front of it). DDP has already reduced the gradients, so both ranks compute the
  same update from the same inputs; the per-parameter arithmetic (apex fused Adam, fp32 master
  weights, fp32 gradients) is unchanged. Tier N0.
* YOCO_OPT_DDP_BUCKET_MB=<int>: DDP gradient bucket size (torch's default is 25 MiB).
* YOCO_OPT_SKIP_MASTER_ZERO=1: skip the memset of the fp32 master gradients (the copy that
  follows overwrites them completely). Tier N0.

1.4 hRound 5 — fused gradient cast-and-scale (Triton), N0
Profile of the current best (/tmp/r8/profile, 1.1756x) put the two memory-bound
optimizer kernels at the top of the update:

| kernel | calls | ms/update |
|---|---|---|
| unrolled_elementwise_kernel<direct_copy> (bf16 grad -> fp32 master grad) | 1200 | 12.9 |
| elementwise_kernel<BinaryFunctor<float>> (master grad *= scale) | 1200 | 12.3 |
| multi_tensor_apply<AdamFunctor> (apex Adam) | 825 | 28.7 |
| ncclDevKernel_AllReduce_Sum_bf16 | 595 | 60.9 (mostly overlapped) |

The cast reads 2 bytes and writes 4 bytes per element, the scale reads 4 and writes
4: 40.6 GB of HBM traffic per update for two passes over the model, in 480 small
kernels (one per parameter) that reach only ~1.0-1.9 TB/s.

yoco/models/fused_grad.py (YOCO_OPT_FUSED_GRAD_SCALE=1) does both in one Triton
kernel: it reads the bf16 gradient, converts it to fp32, multiplies it by the scale
and writes the fp32 master gradient.  All the parameters are handled by **one
launch** (the kernel walks a table of the parameter addresses, built once from the
shapes), so the launch overhead is one kernel per update instead of 480.

The scale (the data-parallel size over the sample size, times the clipping
coefficient) is only known after the gradient norm, so the norm is computed from the
bf16 gradients instead of from the fp32 master gradients.  apex's fused L2 norm was
probed to return the *same* value for a bf16 tensor and for its fp32 image
(/tmp/probe_l2.py, bitwise equal on four tensor lists), so the clipping
coefficient is unchanged.  The cast-and-scale is bitwise equal to
copy_ + mul_ (probed on four tensor sizes, /tmp/probe_engine.py).

* time (/tmp/r5/time_fused): 0.1803 s/update, speedup 1.2956 (from 1.1756).
* check --quick with the same switches but without the RMSNorm compile
  (/tmp/r5/quick_nofuse): PASS, tier N0 - 9616 recorded tensors bitwise
  identical to the reference, 0 exact failures.  So this change is bitwise
  neutral; the only non-bitwise change in the tree is the compiled RMSNorm (N1,
  already validated by check --n1).

2.3 hRound 7 — fused Adam (Triton), N0
The apex fused Adam was the largest single kernel of the update: 825
multi_tensor_apply launches per update, 28.7 ms of kernel time at about 2.8 TB/s.
apex's FusedAdamV2 runs in ADAM_MODE_1 (decoupled weight decay):

    m = beta1*m + (1-beta1)*g ; v = beta2*v + (1-beta2)*g*g
    m_hat = m/bc1 ; v_hat = v/bc2 ; denom = sqrt(v_hat) + eps
    update = m_hat/denom + decay*p ; p = p - lr*update

with bc = 1 - pow((double)float(beta), step) — the beta is rounded to fp32 first,
which is what apex does (float beta = ... then std::pow((double)float_beta, step));
using the Python double beta gives a different bias correction and a different result.

yoco/models/fused_grad.py (YOCO_OPT_FUSED_ADAM=1) replaces
fairseq.optim.fused_adam.FusedAdamV2.step with one Triton launch for all the
parameters (4.1 TB/s, measured over 26 M elements).  The kernel uses
tl.math.fma(beta1, m, (1-beta1)*g) (nvcc contracts the same way), plain division
and tl.sqrt (not div_rn/sqrt_rn), and it writes the **bf16 model weights in the
same pass**, so the separate master -> model copy of round 6 is no longer needed
(the weight-cast override then skips its copy).

* time (/tmp/r8/time_adam): 0.1667 s/update, speedup 1.4013 (from 1.3371).
* check --quick without the RMSNorm compile (/tmp/r10/quick_n0): PASS, tier
  N0 — 9616 recorded tensors bitwise identical to the reference, 0 exact failures.
* Full check with the submitted switch file (/tmp/r11/check): PASS,
  speedup 1.4013, tier N1 (the only non-bitwise change is the compiled
  RMSNorm); gate 3: every one of the six endpoints within 0.81 sigma (bound 3 sigma).
2.3 hRound 8 — where the time goes now (profile of the current best)
The trace of the reference (/tmp/r8/profile) says the update is **launch bound in
the forward pass**: per update the GPU is busy 175 ms (profiled) out of a 225 ms
window and idle 50-67 ms, and most of that idle is inside the model forward
(## self.mixer 19 ms/update, self_decoder 3.8, cross_decoder 3.2).  The
backward is GPU bound (its compute is longer than the CPU work that drives it).

Two causes:

* the forward issues about 3300 kernels per update (780 of them GEMMs) and the
  Python overhead of megatron's parallel linear layers (two autograd.Function
  nodes per layer and per direction, for a copy/reduce that is the identity with
  one model-parallel rank) leaves the GPU waiting;
* 119 NCCL all-reduce calls per update (the DDP buckets are 25 MiB, but a single
  FFN weight is 50 MB, so every bucket holds about one FFN weight): 59 ms of
  NCCL kernel time at about 200 GB/s, well below the NVLink bandwidth.

4.3 hRound 15 — a fused RMSNorm of our own, in Triton (N1)
The compiled RMSNorm cost about 320 us of CPU time per call (146 us forward,
174 us backward) and is called 54 times per update: about 17 ms of the host
time of an update, and the forward pass of the update is GPU bound, so the
host time shows up directly in the wall clock.

YOCO_OPT_TRITON_RMSNORM=1 replaces it with one Triton kernel per direction
(yoco/models/triton_rmsnorm.py), keeping the rounding of the reference: the
normalized value is rounded to bf16 *before* it is multiplied by the weight,
and the gradient of the weight is the sum of the bf16 products of the incoming
gradient and the rounded normalized value.  Against the eager reference, 29 of
6.29M elements of the output and 67 of 6.29M elements of the input gradient
differ by one bf16 ulp, and 6 of 3072 elements of the weight gradient differ by
one ulp — that is the order of the reduction of the mean of the squares, and
nothing else.  This is *much* closer to the reference than the compiled
version, which differed on almost every element.

* time (/tmp/r22/time_triton): 0.1600 s/update, 1.4600 — *worse* than
  the compiled version.  The profile (/tmp/r22/profile) showed why: the
  gradient of the weight was reduced by three programs only, and that kernel
  took 188 us per call (33 GB/s).  The host time did not change (0.171 s per
  update): the GPU was the bottleneck, not the host.
4.3 hRound 16 — the gradient of the weight, reduced in two stages (N1)

5.4 hRound 18 — the size of the DDP gradient buckets (N0)
With 25 MiB buckets (torch's default) the reduction of the 6.3 GiB of bf16
gradients is 119 small NCCL calls per update; every one of them has a fixed
cost and the two ranks have to meet at each of them.  YOCO_OPT_DDP_BUCKET_MB
sets the size of the buckets (fairseq passes bucket_cap_mb to torch's DDP
explicitly, so the value has to be overridden, not defaulted — the first
version of the switch did nothing, see the commit a85d6ce).

* 50 MiB: 0.1508 s/update, 1.5491
* 100 MiB: 0.1505 / 0.1506 s/update, 1.5522 / 1.5511
* 200 MiB: 0.1506 s/update, 1.5511

The size is saturated between 100 and 200 MiB, so 100 MiB is kept.  The values
of the reduced gradients do not depend on the size of the buckets, so this is
N0.

6.2 hRound 21 — the order of the gradient buckets (N0, no gain)
Profile.  The trace of the last update of /tmp/r24/profile (164 ms profiled,
150 ms real) gives the timeline of the update:

| phase | window (ms) | note |
|---|---|---|
| forward | 2.8 – 38.9 | 835 kernels, the CPU issues them faster than the GPU runs them |
| backward | 38.9 – 112.5 | the gradient reduction runs from 50 to 124 ms |
| *gap* | 112.5 – 124.8 | 12.3 ms with nothing to do: the reduction of the last buckets |
| clip + cast | 124.8 – 135.1 | the L2 norm (3 ms) and the fused cast and scale (5.2 ms) |
| Adam | 135.1 – 162 | the fused Adam, 25 ms, at 4.1 TB/s |
| tail | 162 – 164.3 | the event based update timing of the bench |

The 122 NCCL kernels of the reduction are 0.2-0.35 ms each (100 MiB at the full
400 GB/s) with 0.2-1 ms gaps: the reduction is not bandwidth limited but *latency*
limited, it waits for the gradients.  The gradients of the last 1.2 GiB (the output
projection and the embedding) are only ready at the end of the backward, so their
reduction is not hidden: 12.3 ms of the update are the reduction of gradients that
were ready long before.

Change.  torch's DDP fills the buckets in the order of the registration of the
parameters and then reverses the list of the buckets, so the bucket that is reduced
first holds the gradients that the backward produces first.  The YOCO model
registers its parameters in the order of the forward pass, so the gradient of the
output projection -- the first one the backward produces -- is registered second
and lands in one of the last buckets.  YOCO_OPT_DDP_BUCKET_ORDER=1
(yoco/models/optim_overrides.py) moves the parameters of the output projection to
the end of the list that the reducer sees, so that their gradient is reduced first.
The reduced values do not depend on the grouping, so this is N0.

* time (/tmp/r21/time): 0.1503 s/update, speedup 1.5542 (the current best is
  0.1505 / 1.5532): no gain, the difference is inside the noise (0.5 %).
* The switch stays off.

So the 12.3 ms are not the order of the buckets: the reduction of the last buckets
is exposed because it cannot start before the gradients are ready, and the
gradients of the output projection are ready *late* in the backward as well (the
wgrad of the output projection is the first GEMM of the backward, but the reduction
of the buckets is a chain: a bucket is only reduced when the previous one is done).

argument, so the compiled kernel is the same even though the learning rate and
the bias corrections change at every update.
