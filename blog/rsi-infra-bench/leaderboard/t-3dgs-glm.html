Start: ~06:25. Class: memory traffic of the SH-coefficient gradient chain, tier N1.

Profile of the R4 tree (/tmp/r5/profile, steps 7000–7019, P≈1.28M): GPU busy ≈ 7.8 ms/step vs 7.6 ms/step wall → the sync removals left essentially no idle; the remaining work is kernel time. Per step: PerGaussianRenderCUDA (bwd) 2.348 ms (30%), renderCUDA (fwd) 1.392 (18%), fused Adam 1.130 (14.5%), preprocess bwd 0.489 (6.3%), duplicateWithKeys 0.484 (6.2%), radix sort 0.225, zeros/fill ~0.30, SSIM 0.134, norm+div ~0.19.

Change (GS_OPT_SH_ADAM, off by default): the SH gradient of a point is basis_j(dir) * (clamp-masked per-point color gradient) — exactly what BACKWARD::preprocess materializes into dL_ddc/dL_dsh (P×1×3 + P×15×3 ≈ 240 MB zeroed + written every step, then read back by Adam). The fused path:
- backward.cu: computeColorFromSH/preprocessCUDA skip the dL_ddc/dL_dsh writes when fusing (the dL_dmeans direction term still runs, so shs is still read).
- rasterize_points.cu: in fused mode the two gradient tensors are 1-element stand-ins (their zeroing disappears); the backward returns the byte offset of clamped in the geom buffer.
- adam.cu (new ADAM::shAdamUpdate): a 2-thread prep kernel advances the two step counters on device (as torch's fused kernel does) and precomputes the bias corrections; the main kernel walks P×(M·3+3) elements, recomputes the SH basis per element (same formulas/values as computeColorFromSH, gated by the active degree like the original's deg > 0/1/2 nesting), and applies torch's fused-Adam update (m = m·β1 + g·(1−β1), v = v·β2 + g²·(1−β2), p −= (lr/bc1)·m/(√v/√bc2 + eps)). Elements beyond the active degree and invisible points get g = 0, exactly the zeros the reference materializes; every element is updated (dense, like the reference).
- diff_gaussian_rasterization/__init__.py: in fused mode the backward stashes (dc, sh, means3D, dL_dcolors, geomBuffer, clamped offset, campos, degree) and returns None as the dc/sh input grads (so .grad stays None); consume_sh_grad(f_dc, f_rest) hands the stash to the optimizer when it matches exactly those parameter tensors.
- scene/gaussian_model.py (_ShFusedAdam, used when both Adam switches are on): step() runs the fused kernel for the f_dc/f_rest groups (torch-style lazy state init, float32 step/exp_avg/exp_avg_sq) and then calls super().step() for the other four groups. When densification/pruning/opacity-reset has replaced a parameter tensor since the backward, the reference optimizer sees a None gradient and skips (no update, no step increment); the identity check reproduces that exactly.

Numerics: the gradient values are the same formulas on the same inputs (per-point, no atomics, same nesting) → bitwise-equal g up to compiler FMA choices; the Adam update replicates torch's fused kernel formula (powf-based bias corrections), so ulp-level differences are possible → N1, same class as the R1 foreach→fused switch that passed gate 3 with margin.

Traffic saved ≈ 0.7 GB/step (dL_dsh/dL_ddc zero + write + Adam grad read), expected ~0.4 ms/step.

Why it lost (working theory, to be confirmed by the R6 profile): the fused kernel parallelizes over the P×(M·3+3) ≈ 61M elements, so j = e/3 varies *within every warp* and the 15-way if-chain that evaluates the SH basis diverges — each warp serially executes most of the 15 branch bodies (~15× the basis ALU). The traffic the fusion saved (~0.4 GB/step ≈ 0.2 ms) is smaller than that divergence penalty. A branch-free (predicated-arithmetic) basis, or a thread-per-point layout like the original preprocessCUDA (sequential over j ⇒ no divergence), should bring the kernel to ~0.5 ms vs the ~0.63 ms it replaced — a ceiling of only ~+0.1 ms/step, so the fix is deferred behind bigger fish.

2.8 hRound 7 — shared-memory staging of the backward's per-pixel accumulators (GS_OPT_BWD_PIXCACHE)
Start: ~07:57. Class: the #1 hotspot, PerGaussianRenderCUDA 2.48 ms/step (30%). The kernel launches one 32-thread block per bucket; every cascade iteration lane 0 issues ~10 scalar global loads (sampled_T, sampled_ar×3, pixel colors×3, final_T, n_contrib, dL_dpix×3) that feed the next iteration — a long latency chain where each 4-byte load drags a 32-byte sector (8× amplification), and the pixel-indexed ones are re-read by every bucket of the same tile.

Change (GS_OPT_BWD_PIXCACHE, off by default): PerGaussianRenderCachedCUDA — a 256-thread block covers 8 consecutive buckets; each active warp stages its own per-pixel checkpoint (4 KB) coalesced into shared memory, and the block stages the tile's per-pixel data once for all 8 warps. Values identical (lossless float32 staging, same math) → N0 up to atomic-order rounding. Depth-enabled cameras keep the original kernel (also keeps static smem at 42 KB < the 48 KB limit; 62 registers). pixel_cache threaded GaussianRenderSettings → binding → Rasterizer::backward → BACKWARD::render; use_cache falls back to the original global loads when a block's active warps span two tiles.

First attempt — ERROR at step 10701 (/tmp/r7/time): illegal memory access after a densification step. A/B with the judge's entry (traj mode, 3100 steps, seed 0) showed the training had diverged: final count 10,432,987 vs the switch-off 945,796. Root cause: the per-warp staging wrote s_T[warp_id][threadIdx.x] — each warp staged only the 32 entries at threadIdx.x ∈ [warp_id·32, warp_id·32+32) of its own 256-entry array; 224 of 256 checkpoint entries per bucket were uninitialized shared memory. Garbage T/ar → garbage gradients → runaway densification (the quick gate still PASSED — it checks the *steps* at which the count changes, not the counts; a lesson: check --quick cannot see gradient-value bugs). The garbage params then made the next forward's tile ids undefined → the fault. Fix: each warp's 32 lanes walk e = lane, lane+32, …, lane+224 (all 256 entries, coalesced).

Value validation (the quick gate can't see it, and the backward's atomics make bitwise comparison impossible even run-to-run): three 500-step entry runs — off, off, on (seed 0, before densification). Pairwise max|Δparam|: off-off (pure atomics noise) 1.26e-01/7.3e-01/4.1/1.19/4.9e-01 (xyz/dc/opacity/scaling/rotation) vs off-on 1.22e-01/8.3e-01/4.0/1.16/4.6e-01 — same magnitude on every parameter → the cached kernel is value-equivalent within the noise floor (N0 in exact arithmetic; differences are atomic-order rounding, the same class as any rerun).
