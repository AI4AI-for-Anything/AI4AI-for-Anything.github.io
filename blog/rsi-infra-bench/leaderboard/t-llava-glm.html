0.7 hRound 4 conclusion — ZeRO-2 rejected: its forward is not the reference's forward
The check --quick with the z2 config (/tmp/r4/quick-z2) showed all exact items pass (RNG fingerprint, per-step sample multisets, optimizer/precision settings, dtypes) but only 32/4724 tensors bitwise — the loss, gradients, master updates and Adam states all differ in deterministic mode.

Instrumented bisect (throwaway tree copy, judge time runs, /tmp/rngdump-z3 vs /tmp/rngdump-z2, /tmp/r4/diag-z3c + diag-z2b):
- Initial weights: 12/12 key parameter hashes identical (lm_head, embed, q/k/o_proj, norms, gate_proj, mm_projector, CLIP tower) at train start.
- Global CPU RNG state at train start: identical (5feb54a4...), and at dataloader iteration: identical (60c7dd32...); the sampler's first 64 indices are identical → same batches, same within-step split.
- Yet the losses differ (z2 step-9 loss 1.0892 matches the z2 sweep pattern, not the reference's 1.0875).

So with identical weights, data, order and RNG, DeepSpeed stage 2 computes different forward values than stage 3. The only remaining difference is the parameter *storage*: stage 2 keeps every weight as a slice of one flat bf16 buffer, stage 3 gathers each weight into a fresh tensor — same values, different memory layout, different GEMM kernel selection/reduction order. That is intrinsic to the engine and not honestly patchable (the flat-buffer views are load-bearing for ZeRO-2's gradient/optimizer plumbing).

Verdict: ZeRO-2 is rejected — gate 1's first-logged-loss band (0.5%) fails at −0.585% systematically. The ~110-119 ms/step it saves (1.096-1.099× vs 1.050×) is real but unreachable under the gates. The budget control (z3b62) also bought nothing (2626.8 vs 2621.2 ms). Submission stays at the validated N0 config: LLAVA_CKPT_BUDGET=55, PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True, LLAVA_FUSED_ROPE=1 (1.0496×, gate 2 bitwise 4724/4724).

Lesson: a ZeRO-stage change is not numerics-neutral on this stack even at world size 2 — validate with check --quick before believing any "same math" argument about the engine's memory management.

1.1 hRound 6 by-product — the fused RoPE never ran (round-3 attribution corrected)
Mining the profile's python frames showed apply_rotary_pos_emb_fused called 55×/step and _rope_supported 55×/step with zero Triton kernels in the trace: the round-3 fused rope silently fell back to the eager chain on every call. Root cause: transformers 4.37.2 builds position_ids as [1, S] (arange().unsqueeze(0), never expanded), so cos[position_ids] is the broadcast form [1, S, D], and _rope_supported required x.shape[0] == cos_g.shape[0] (16 ≠ 1). The eager rope chain is visible in the profile: 524 bf16 muls (119.2 ms), 372 aten::cat (43 ms), 174 neg (16.7 ms) ≈ ~190 ms/step of rope kernels that the fusion was supposed to replace.

Corollary: round 3's −44 ms was the LLAVA_CKPT_BUDGET raise (45→55) alone, not the rope fusion; the "fused RoPE" entry in the gain breakdown below was wrong until now.

Fix (committed 40fa515, tier N0): accept cos_g.shape[0] in (1, x.shape[0]) and read table row 0 via a zero batch stride (value-identical to broadcasting); plus do_not_specialize=["S"] so Triton compiles exactly one variant per direction regardless of the padded length's divisibility-by-16 class (verified: 2 cache entries across S ∈ {512, 777, 1627, 2048}) — otherwise a mid-run class change would compile inside a timing window and invalidate it. Bitwise GPU test vs the eager reference (/tmp/test_rope2.py): fwd outputs, q/k grads, broadcast + per-row forms, deterministic mode, H 8/32, D 64/128 — ALL PASS. Timing in round 7.
